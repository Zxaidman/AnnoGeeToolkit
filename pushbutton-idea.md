## 2026-09-19 05:41 UTC

**Idea name:** Grid Sync — a direct pushbutton for the already-working GRIDS-sheet engine, so setting out (or resyncing) a structural grid stops requiring the bridge, an HTTP call, or an Excel macro

**Potential:**
Laying out a project's grid system is one of the very first things a structural modeler does and one of the most repeated after that — every bay-spacing revision means deleting or nudging a run of grids by hand, one at a time, and retyping bubble names to match. The tool to do this from a spreadsheet in one pass **already exists, fully built and tested**, and almost nobody who opens Revit can reach it. `anongee_toolkit.rc_automation.datum` carries the whole engine — `GridRow`/`GridPlan` (`datum.py:623,649`), `parse_grids()` reading a GRIDS sheet's Name/X1/Y1/X2/Y2/Angle columns via `_grid_header()` (`datum.py:673,730`), `grid_line()` resolving whichever columns a row actually filled in against a sheet-wide `default_length()` for angle-only rows (`datum.py:765,784`), and `plan_grids()` (`datum.py:855-961`) matching sheet rows to existing model grids by name-or-folded-name, refusing to move a grid whose direction disagrees (`"changing a grid's direction means recreating it, which loses anything dimensioned or constrained to it"`, `datum.py:918-925`) and refusing to create a second grid on a line already occupied (`_on_line`, `datum.py:963-970`). `anongee_toolkit/commands/grids.py` wires that straight to the API: `_apply()` opens one `TransactionGroup`/`Transaction`, calls `Grid.Create` for a new row and `ElementTransformUtils.MoveElement` for a matched one that only needs sliding onto the sheet's line (`grids.py:107-166`), and the whole thing is declared in the bridge registry as `"grids.sync"` with its own dry-run default (`registry.py:108-110`). The catch is entirely in how a modeler is meant to reach it: `commands.grids.run(uiapp, envelope)` only runs as a bridge job — the handler is bound by `commands.register_all()` inside `Bridge Listener.pushbutton`'s own `ensure_ready()` (`Bridge Listener.pushbutton/script.py:288-299`), which itself only happens once that pushbutton's window has been opened in the session, and even then a job has to arrive as a file in the outbox, written either by the HTTP route or, per `Bridge Check.pushbutton`'s own docstring, tested "from Excel instead" (`Bridge Check.pushbutton/script.py:1-9`) — i.e. from a macro a modeler has to have and know how to run. There is no equivalent to what levels got: `AutoLevel.pushbutton` gives levels a real interactive pushbutton, but it turns out to be a fully separate, independently-built engine (`anongee_autolevel/planner.py`, `textparse.py`, `naming.py`, `revit_ops.py`) that never imports `datum` at all — every "datum" hit inside it is the unrelated `DatumInput` elevation-offset field, confirmed by reading every match. So grids are worse off than levels: nothing in the repo lets a modeler point at a GRIDS workbook and press a button. The already-logged **Grid Mark Assistant** (2026-09-13) reads existing `DB.Grid` geometry to number columns and beams off it, but has nothing to say about creating the grids themselves — it explicitly starts from grids that already exist. This is the missing first step ahead of it. On the market, spreadsheet-driven grid setout exists only as one-off Dynamo graphs with no dry-run preview or direction-safety guard, or as a line item inside paid whole-project structural add-ins (Naviate Structure, BIM One's structural modules) sold per seat as part of a much larger bundle; nothing free turns a bay-spacing table into a checked, previewed, one-undo-step grid layout.

**Description:**
`Grid Sync.pushbutton` (new tool, `Essential.panel/StrucBIM.stack`, sibling to `Convert Slab.pushbutton` and `RoundElementDist.pushbutton`, the stack's two other structural-geometry tools):

1. **Pick a workbook** — a plain file-open dialog for the `.xlsx`, defaulting to the GRIDS sheet name `datum.SHEET_GRIDS` already expects, with a text field to override the sheet name for a workbook that names it differently.
2. **Parse + plan** — calls `datum.parse_grids()` then `datum.plan_grids()` against the model's current grids (the same `_existing()` read `commands/grids.py:87-104` already performs through `anongee_toolkit.structural.grids`), entirely off-Revit until the moment Apply is pressed.
3. **Preview checklist** — one row per sheet grid: name, resolved line, action (**create** / **move Δn mm** / **already matches** / **blocked — direction disagrees** / **blocked — line already claimed by "X"** / **invalid — duplicate name on the sheet**), reusing the same tick/untick-before-anything-happens shell `Convert Slab.pushbutton` and every other pre-flight tool in the repo already runs on. Blocked and invalid rows come pre-unticked, matching that shell's convention.
4. **Report only / Apply** — the same two-mode toggle `Convert Slab.pushbutton` offers; Apply calls the exact `_apply()` transaction logic `commands/grids.py` already ships (or that module directly, since it is plain, Revit-only code with no bridge dependency baked into the write path itself — only `run()`'s envelope-unwrapping wrapper is bridge-shaped).
5. **Result** — created / moved / already-matched / blocked counts, with the same per-row messages `plan_grids()` already generates (a grid the sheet doesn't mention is left alone and reported, never deleted), exportable through the `openpyxl` path `Export Schedule.pushbutton`/`BBS Generator.pushbutton` already use.

**Implementation:**
- Imports `anongee_toolkit.rc_automation.datum` and `anongee_toolkit.rc_automation.excel_engine.read_grid()` directly — the same modules `commands/grids.py` already imports (`grids.py:31-32,50`) — and reuses `commands.grids._apply()`/`_existing()` verbatim rather than re-implementing them a second time; the only new code is the file picker, the checklist UI and the plain (non-envelope) call into those two functions.
- No bridge, no `envelope`, no `Bridge Listener.pushbutton` session requirement — this button opens its own document handle and runs the transaction inline, on the click, the same way `Convert Slab.pushbutton` and `RoundElementDist.pushbutton` already do; `commands.grids.run()`'s envelope-unwrapping shell (`grids.py:28-84`) is not reused, since a modeler at a pushbutton already has the workbook path and dry-run toggle a UI control gives directly.
- Same modeless window shell (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`) every other multi-step tool in the repo runs on, and the same `openpyxl` report export `Export Schedule.pushbutton`/`BBS Generator.pushbutton` already prove.
- Ships with its own `bundle.yaml`/`README.md` per the root README's versioned-tool layout, in `Essential.panel/StrucBIM.stack/`.
- Worth doing the same for `levels.sync` right alongside this, since `AutoLevel.pushbutton` — confirmed above — does not actually cover that command's Excel-driven path either; a `Level Sync.pushbutton` built the same way would close both gaps with one shared UI pattern rather than one.

**Future update:**
- Extend the same picker to `footings.sync`/`columns.sync`/`beams.sync`/`slabs.sync`/`stairs.sync` (`registry.py:117-132`) once Grid Sync proves the "bridge command, no bridge required" pattern — each is exactly as bridge-only today as grids.sync is.
- "Since last run" diff mode, the same shape already logged for Type Matrix Generator, Sheet Issue Kit and the Analytical-Physical Alignment Auditor, so a resync after a spacing revision reports only what actually moved.
- Feed the resolved grid set straight into the already-logged Grid Mark Assistant as an optional next step in the same window, so setout and mark-numbering become one continuous run for a new project instead of two separate button presses.
- A saved-workbook-path-per-project setting, so a re-run after the first doesn't need the file picker again.

## 2026-09-19 00:41 UTC

**Idea name:** Workset Assigner & Hygiene Auditor — rule-based batch workset assignment by category/level/keyword, plus a whole-model audit for elements sitting on the wrong (or still-default) workset

**Potential:**
A repo-wide grep for `Workset`, `WorksetTable` and `WorksetKind` across every `script.py` and every `anongee_toolkit` module turns up exactly one hit outside third-party library code: `ConvertFloor.pushbutton/script.py:897`, inside `copy_instance_params()`, which copies `BuiltInParameter.ELEM_PARTITION_PARAM` (the workset parameter) from a source element to its recreated counterpart alongside `PHASE_CREATED`/`PHASE_DEMOLISHED` — a narrow, single-element "don't let a slab↔foundation recreate silently drop the element onto whatever workset happens to be active" preserve, not an assignment feature or an audit of any kind. The only other place the repo even reads worksharing state is `startup.py:298`, which logs `doc.IsWorkshared` into a startup diagnostics payload and does nothing with the value beyond that — it never gates a feature, never lists a workset, never touches `WorksetTable`. Nothing in the toolkit creates a workset, assigns one to a batch of elements, or reports which elements disagree with a firm's own workset standard. In practice this is one of the most common, slow-burning hygiene problems on any workshared structural project: a new element created while a modeler forgot to switch the active workset lands wherever that workset happened to be pointed — often the office-standard "Workset1" or someone else's discipline workset — and Revit gives no warning; the only native fix is switching the active workset, running Manage → Select All Instances per category, and re-checking the Properties palette workset by workset, a process nobody repeats often enough for it to actually hold, which is exactly why worksets on a mature project so often stop meaning anything (they exist to support partial-open scoping, borrow-performance separation, and discipline-level permissions, all of which degrade the moment elements are scattered across the wrong ones). A schedule with a Workset column bulk-edited in Excel and reloaded is the usual workaround, and it edits values with no rule behind them and no record of what changed or why. This is a distinct gap from two already-logged ideas that sit close to it: **View Graphics Sync** (2026-09-15 05:39) proposes propagating *view-level* workset visibility graphic overrides between views — a display setting, never touching which workset an element actually lives on; and **ConvertFloor**'s own copy is scoped to keeping one recreated element's workset unchanged during a conversion it already performs for other reasons, not to deciding what any element's workset *should* be. On the market, bulk workset assignment/audit tools exist only as one module inside large paid BIM-management suites sold per seat (CTC BIM Tools' Workset Manager, Ideate BIMLink, Avail) or as one-off Dynamo graphs shared without any reusable rule table or audit report; nothing free reads a firm's own category/level naming convention and both audits and fixes workset drift against it.

**Description:**
`Workset Assigner.pushbutton` (new tool, `Essential.panel/Bulk Tool.stack`, sibling to `Bulk Rename.pulldown`, `Bulk Delete.pulldown` and `Rebar.pulldown` — the stack that already owns "apply one rule across many elements at once" tools):

1. **Guard** — if `doc.IsWorkshared` is false (the same flag `startup.py:298` already reads, here made load-bearing instead of purely informational), the tool explains why and exits; no transaction risk on a non-workshared file.
2. **Rule table** — rows of `condition -> target workset`, where a condition is a category plus an optional refinement (level, a parameter value/contains-text check — e.g. "OST_StructuralColumns on Level 02 and above → WS-Structure-L02", "Family Name contains 'Rebar' → WS-Rebar"), evaluated top to bottom, first match wins. Rules load from / save to a per-project or per-office `workset_rules.json`, so one firm standard is written once and reused project to project instead of retyped.
3. **Audit pass (default, read-only)** — scans every element in scope (whole model / active view / selection, the same three-way picker `Convert Slab.pushbutton` already offers) and compares its current `ELEM_PARTITION_PARAM` against what its first matching rule says it should be. Flags: **wrong workset** (a rule matches and disagrees), **unmatched** (nothing in the rule table reaches it — commonly everything still sitting on the un-renamed default workset), **host mismatch** (a hosted instance's resolved target workset would disagree with its own host's workset — flagged rather than silently forced, since a shared/owner-controlled workset isn't always wrong to differ from). Nothing is written in this pass; it exists as its own standalone worksharing-hygiene report even before Apply is used.
4. **Preview checklist** (the same shell every pre-flight tool in the repo already runs) — one row per flagged element: category, current workset, target workset, matching rule name; rows tick/untick before anything changes.
5. **Apply** — one `Transaction`; creates any workset a rule names that doesn't exist yet (`Workset.Create`), reported before creation rather than appearing silently, then sets `ELEM_PARTITION_PARAM` per ticked row.
6. **Report** — assigned / already-correct-skipped / unmatched / host-mismatch-flagged / worksets-created counts, exportable through the same `openpyxl` path `Export Schedule.pushbutton`/`BBS Generator.pushbutton` already use, giving a BIM manager a paper trail for a worksharing audit.

**Implementation:**
- New `anongee_toolkit.revit.worksets` module — first in the repo to touch `Autodesk.Revit.DB.Workset` / `WorksetTable` / `WorksetKind` at all (confirmed by the zero-hit grep above): `list_worksets(doc)`, `find_or_create(doc, name)` wrapping `Workset.Create`, `current_workset(element)` reading `ELEM_PARTITION_PARAM`, `evaluate_rules(element, rules)` returning the first matching rule or `None`.
- Rule-condition matching (category + level/parameter refinement) reuses the same category-and-condition shape `MultiFilterParameter.pushbutton`'s filter engine already implements (Categories tab + operator/value condition rows), rather than inventing a second condition language — a rule row here is effectively a Filter-Parameter condition plus a target workset instead of a target parameter value.
- The `doc.IsWorkshared` gate reuses the exact check `startup.py:298` already performs for telemetry, now driving a feature instead of only being logged.
- `workset_rules.json` beside `script.py`, mirroring `slab_convert_config.json`'s and `tag_sweep_config.json`'s override-by-config convention already used across the repo.
- UI: the same checklist-with-per-row-status shell (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`) every other multi-step tool in the repo runs on.
- Sits in `Essential.panel/Bulk Tool.stack/`, own `bundle.yaml`/`README.md`/`CHANGELOG.md` per the root README's versioned-tool layout.

**Future update:**
- Level-range rule conditions resolved off the same sorted level table `AutoLevel.pushbutton` and the logged View Range Manager idea already build, so a rule can say "Level 05 and above" without hardcoding a level name that changes when a level is renamed.
- Optional auto-fix for host-mismatch rows once flag-only behaviour is proven safe on real projects.
- Hook into `BIMGeneration.pushbutton`/`RC Automation.pushbutton`'s own element-creation paths as an opt-in post-step, so newly created columns/beams/slabs land on the correct workset the moment they're created instead of needing a later sweep.
- "Since last run" diff mode — the same shape already logged for Sheet Issue Kit, Type Matrix Generator and the Analytical-Physical Alignment Auditor — so a re-audit reports only what drifted since the last pass instead of the whole model again.

## 2026-09-18 15:43 UTC

**Idea name:** Revision Cloud Sync — model-diff-driven native `RevisionCloud` placement that turns "what changed since the last issue" into drawn, tagged, code-native markup, instead of a modeler eyeballing a redline and sketching clouds by hand

**Potential:**
Every issued set that goes out a second time needs revision clouds around whatever actually changed, and today that is entirely manual and entirely memory-based: a modeler compares the new plan against the last issue (or just remembers "I moved that beam and added two footings"), picks Revit's native Detail → Revision Cloud tool, sketches a rough polygon by hand around each changed area, on every affected view, then checks the sheet's revision schedule to make sure the right revision number shows against the right sheet — repeated, from memory, every single issue, with no model-side confirmation that a cloud actually covers everything that moved. A repo-wide search for `RevisionCloud`, `GetAllRevisionIds`, `Revision.Create` and `SetAdditionalRevisionIds` across every `script.py` and every `anongee_toolkit` module returns zero hits anywhere in `AnonGee.tab` or the toolkit — nothing in this codebase has ever touched Revit's own `Revision`/`RevisionCloud` object model. What the repo does already have, and what makes this worth building now rather than from nothing, is a fully-working diff engine solving the identical shape of problem for a narrower population: `BBS Generator.pushbutton/core/revision_tracker.py` already saves a per-export JSON sidecar (`_sidecar_path`/`save_revision`, `revision_tracker.py:29-58`) keyed by bar identity, computes each `BarRecord`'s own change fingerprint via `_compute_hash()` — an md5 of a sorted-keys JSON payload of its own tracked fields (`bar_record.py:50-61`) — and on the next export loads the previous sidecar and classifies every record `new`/`changed`/`deleted`/`same` (`compare_revisions`, `revision_tracker.py:80-119`). That engine exists purely to colour rows green/yellow/red in an Excel bar-bending schedule; it has never been pointed at the model's own elements, never grouped a change by which view shows it, and never created a single Revit annotation object. This is distinct from the two closest logged ideas: Sheet Issue Kit (2026-09-15 15:40) proposes its own sidecar diff purely to skip re-exporting an unchanged sheet to PDF/DWG/NWC — it never draws a cloud, never touches `Revision`/`RevisionCloud`; Warning Auditor (2026-09-12 10:39) reads Revit's standing warning log, not a diff against a prior model state, and produces nothing on a sheet. On the market, revision-cloud creation itself is native to Revit (draw-by-hand only), and automated "what changed, cloud it" workflows are sold only as line items inside large paid production suites (CTC BIM Tools, BIM One) that offer manual cloud-from-selection helpers, or paid tools (Naviate/Ideate-class) that manage revision sequencing/numbering but not diff-driven cloud placement — nothing found diffs a model against a saved baseline and clusters the changed geometry into placed, tagged `RevisionCloud` elements automatically.

**Description:**
`Revision Cloud Sync.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `AutoDIM.pushbutton` and `Export Schedule.pushbutton`) runs in one window:

1. **First run — capture a baseline.** Scope: whole model, active view, or a category checklist (Structural Columns, Framing, Walls, Floors, Foundations, Rebar). For every element in scope, computes a per-element fingerprint — a hash of a configurable parameter set plus its `BoundingBoxXYZ` min/max in mm — and writes it to a per-project sidecar `revision_cloud_log.json` keyed by `UniqueId`, mirroring `revision_tracker.save_revision`'s exact shape (`revision_tracker.py:29-58`) one level up, from bar records to any element.
2. **Later run — diff.** Reloads the sidecar and classifies every in-scope element `new` / `changed` (hash differs) / `deleted` / `same`, the same three-way classification `compare_revisions` already implements (`revision_tracker.py:80-119`).
3. **Group by affected view.** Every eligible plan/section/elevation from `anongee_toolkit.revit.views.get_eligible_views()` (`revit/views.py:36-56`) is checked for which changed elements it actually shows.
4. **Cluster into cloud regions per view.** Changed-element bounding boxes are projected onto the view's sketch plane using `AutoDIM.pushbutton`'s own `project_to_view_plane(pt, view)` (`script.py:57-60`), then merged into regions using `anongee_toolkit.revit.geometry.bounding_boxes_overlap` (`geometry.py:40-59`) with an enlarged, configurable padding tolerance.
5. **Preview checklist** — one row per (view, region): element count, categories, change types present, and the target `Revision` (from `doc.GetAllRevisionIds()`, or "create new revision" inline).
6. **Apply** — one `Transaction`: `RevisionCloud.Create(doc, view, revisionId, curveLoops)` per ticked region, with an optional revision tag at the region's centroid.
7. **Report + rebase** — result table exportable via the same `openpyxl` path `Export Schedule.pushbutton`/`BBS Generator.pushbutton` already use, and the sidecar is rewritten as the new baseline.

**Implementation:**
- New `anongee_toolkit.revit.revision_sync` module: `snapshot(doc, scope)` / `load_baseline()` / `diff(current, baseline)`, a direct generalization of `revision_tracker.save_revision`/`load_previous_revision`/`compare_revisions` (`BBS Generator.pushbutton/core/revision_tracker.py:29-119`) from `BarRecord`-specific fields to a configurable parameter list read through `anongee_toolkit.revit.parameters.get_parameter_value` (`revit/parameters.py:36-82`) plus a bounding box read converted to mm with `anongee_toolkit.revit.units.ft_to_mm` (`units.py:38-40`).
- Hash computation mirrors `bar_record.py:50-61`'s `_compute_hash()` shape exactly.
- View-plane projection and anchor geometry reuse `AutoDIM.pushbutton`'s existing `project_to_view_plane` and `bbox_center`/`element_frame` (`script.py:57-60, 70-150`).
- Region clustering reuses `anongee_toolkit.revit.geometry.bounding_boxes_overlap` (`geometry.py:40-59`) as the pairwise merge test inside a union-find pass.
- New Revit API surface this tool is the first to touch anywhere in the repo (confirmed by repo-wide grep): `Autodesk.Revit.DB.Revision` / `doc.GetAllRevisionIds()` / `Revision.Create(doc)` and `RevisionCloud.Create(doc, view, revisionId, curveLoops)`, plus `ViewSheet.GetAllRevisionIds()`.
- `revision_cloud_config.json` alongside `script.py` (hash fields per category, padding tolerance, deleted-element clouding window), mirroring `slab_convert_config.json`'s override-by-config shape.
- Sidecar `revision_cloud_log.json` follows the same convention `.bbs_rev` already establishes.
- Sits in `Essential.panel/Action.stack/`, own `bundle.yaml`/`README.md`/`CHANGELOG.md`.

**Future update:**
- Converge with Sheet Issue Kit's proposed sidecar diff once it lands, so export-skip and cloud placement share one "changed since last issue" fact.
- Auto-set each affected sheet's revision entry via `ViewSheet.SetAdditionalRevisionIds` once basic placement is proven.
- Fold `BBS Generator.pushbutton`'s own `.bbs_rev` bar-level diff in as a trackable category.
- Per-category padding/cluster tolerance as a config refinement once real projects prove the default tolerance right or wrong.

## 2026-09-18 10:42 UTC

**Idea name:** Column Reinforcement Placer — closes RC Automation's own long-open SCOPE-3/SCOPE-4 gap by finally placing the column main bars and ties it already computes, then continuing them storey to storey with a code-based lap splice and starter-bar projection instead of stopping flush at every pour

**Potential:**
RC Automation's own README states the boundary outright — *"What it will NOT do: Create columns. Their reinforcement is worked out but not yet placed. Lap or start column main bars. Bars stop at the pour; the report says so rather than guessing a lap length."* — and the tool's own `todo-list.md` names this as a tracked, unclosed defect, not a hypothetical: `CRIT-3` (`todo-list.md:98-110`) reads *"reading the run against its own report. Every run says 'Placing 6 footings and 5 columns' and every run creates zero columns and zero column bars,"* with `SCOPE-3 — create columns` (`todo-list.md:320-323`, *"the mains and ties that are already planned. Closes CRIT-3 properly"*) and `SCOPE-4 — laps and starter bars` (`todo-list.md:325-328`, *"explicitly out of scope... recorded here so the exclusion is a decision rather than an omission"*) both still `pending`. What makes this worth building now rather than filed as "someday" is how much of it is already sitting finished and unwired: `anongee_toolkit.rc_automation.rebar_spec` already has `plan_column_mains()` and `plan_column_ties()` (`rebar_spec.py:682-746`) — the tie-set function already builds the three-zone confined-end/middle/confined-end layout IS 13920, ACI 318 Ch.18 and EC8 all require, and the main-bar function's own docstring says exactly what's missing: *"Laps and starter bars are deliberately absent -- the plan says so, the report says so per column, and a bar that stops at the top of the pour is honest about being incomplete in a way a guessed lap length would not be."* `anongee_toolkit.structural.rebar_factory` already knows how to write a column bar once handed one — `_style_for()` (`rebar_factory.py:300-302`) already branches `ROLE_COLUMN_TIE` to `RebarStyle.StirrupTie`, and its own comments (`rebar_factory.py:520,537`) already describe "what column ties come through as" and "what column main bars come through as." The Excel side is equally finished: `rc_automation.models` already parses `COLUMN_TYPES`/`COLUMN_PLACEMENT`/`COLUMN_REBAR` into `ColumnType`, `ColumnPlacement` and `ColumnRebarRow` (`models.py:262,367,490`), with `column_type()`/`column_rebar_for()` lookups (`models.py:568-575`) mirroring the footing equivalents exactly, and `ColumnPlacement`'s own docstring already states *"There is no Height. The column runs from its base level to its top level... a height column would be a second source of truth that disagrees the moment a level moves"* — the multi-storey structure this idea needs is already how the sheet is modelled. Even column placement geometry exists: `anongee_toolkit.structural.columns` (387 lines — `find_symbol`, `ensure_symbol`, `create`, `placed`) is a complete, working module, yet a grep of `RC Automation.pushbutton/script.py`'s own import block (`script.py:127-131`, which imports `rebar_hosts`, `rebar_run`, `footings`, `structure_run`, `element_params`) never once imports it — confirmed by searching every "column" reference in that script.py, which only ever *counts* columns and checks host-eligibility (`script.py:306-307,1324-1332,1402,1436`), never creates or reinforces one. The one place the orchestration layer (`rebar_run.py`) touches column data at all is `resolve_bar_types()` (`rebar_run.py:199-218`), which reads `workbook.footing_rebar + workbook.column_rebar` together purely to resolve bar-type element ids — there is no `plan_columns()` or `place_column()` anywhere beside `plan_footings()`/`place_footing()` (`rebar_run.py:118-258`). So every input this idea needs — the math, the write primitives, the parsed schedule, even the FamilyInstance placement — already exists in the repo, fully built and individually correct, and the only thing missing is the orchestration wiring one already-complete module to the next, plus the one genuinely new piece: continuity across the joint. That last piece is also the one none of the 28 already-logged ideas cover — **Rebar Cage Copier** (2026-09-17) explicitly clones an already-modeler-built cage and deliberately avoids RC Automation's code-standard generation problem entirely; **Lap & Starter-Bar Continuity Auditor** (2026-09-14) only reads *already-placed* rebar to flag short laps, and since RC Automation places zero column bars today (`CRIT-3`), that auditor has nothing to audit for column reinforcement until something like this creates it. On the market, a schedule-driven column cage with real cross-storey lap/starter continuity exists only inside paid, seat-licensed rebar-detailing suites (AGACAD's Rebar for Revit, Naviate Structure, BIM One's structural modules) sold as one feature of a much larger bundle; nothing free reads an Excel reinforcement schedule and auto-continues column steel across a storey joint the way this would.

**Description:**
Lands inside `RC Automation.pushbutton` itself — the natural completion of `SCOPE-3`/`SCOPE-4`, using the exact same workbook, validation, modeless window and chunked-`TransactionGroup` write shell the footing path already runs on, rather than a second, duplicate pushbutton shell:

1. **Match or create the column instance** — for each `ColumnPlacement` row (`models.py:490-518`), find a placed column via the same key-parameter index pattern `rebar_hosts.index_by_key()` already builds for footings, now pointed at `rebar_hosts.COLUMN_CATEGORY` (`rebar_hosts.py:27`, defined and already unused for indexing); when none exists and the run is in "Create structure and reinforcement" mode, resolve the type via `columns.ensure_symbol()`/`find_symbol()` (`columns.py:40-215`) and place it with `columns.create()` (`columns.py:252-276`) between `base_level` and `top_level` — the one import RC Automation's script.py has never made.
2. **Plan one storey segment** — pull `COLUMN_REBAR` rows via `workbook.column_rebar_for(type_mark)` and hand them straight to the already-complete `rebar_spec.plan_column_mains()`/`plan_column_ties()` (`rebar_spec.py:682-746`) using the column's own base→top span — zero new reinforcement math, only the per-column orchestration `_plan_one_footing` (`rebar_run.py:133-185`) already models for pads.

**Potential:**
A shared parameter is identified by its GUID, not its name — Revit only *displays* the name — but every tool a modeler actually touches (the parameter picker, a schedule, the Properties palette) shows only the name, so nothing in the UI ever reveals when a project has quietly ended up with two different "ID" or "Type Mark" definitions bound from two different `.txt` shared parameter files: one from the office master, one baked into a vendor family, a consultant's linked model, or last year's project template before the office file was revised. This is not a hypothetical — it is the precise risk `anongee_toolkit/structural/element_params.py` already documents about itself and only half-guards against. Its own module docstring (lines 17-19) states the danger outright: "creating a second one of the same name would give two different projects two different parameters that read the same on screen," and `_text_definition()` (line 245) guards exactly one path — reusing a definition already present *by name* inside the currently-open shared parameter file before creating a new one. But `bound_names()` (line 113), the function every mode of `RC Automation.pushbutton` calls before writing a single value (`script.py:468`, `_prepare_parameters`), keys its whole "is this parameter already here" answer off `known[definition.Name] = ...` (line 141) — pure name, no GUID comparison anywhere in the function. The same blind spot is load-bearing in the repo's single most-reused matching routine: `ConvertFloor.pushbutton`'s `find_target_param()` (`script.py:866-886`), cited as the shared convention by four other logged ideas (Type Matrix Generator, Convert Column⇄Wall, Schedule Round-Trip, Sleeve & Opening Coordinator) and used by `ConvertFloor.pushbutton` itself for every slab↔foundation conversion, tries `BuiltInParameter` first, `new_el.get_Parameter(sp.GUID)` second — and when that GUID lookup returns nothing (exactly the mismatch case, since the target category's binding carries a *different* GUID for the same name) falls through to `new_el.LookupParameter(d.Name)` at line 883: a pure name match that looks identical in the run report to a clean GUID hit. On the market this exists only as one report deep inside paid whole-project QA/QC suites (Ideate BIMLink's parameter audit, Avail, BIM One's model-checker bundles) sold per seat as part of a much larger tool nobody buys for this one check; no free, standalone GUID-vs-name reconciliation tool exists.

1. **Collect every binding** — `doc.ParameterBindings.ForwardIterator()`, the same enumeration `element_params.bound_names()` already performs (`element_params.py:113-153`), but recording the full `Definition` per name instead of collapsing straight to a category set: name, GUID (when `IsShared`), the category set it reaches, and whether it is instance- or type-bound.

**Idea name:** Lap & Starter-Bar Continuity Auditor — cross-storey rebar lap-splice and starter-bar continuity check for placed column reinforcement

**Potential:**
Every RCC structure's column reinforcement is only as continuous as its lap splices: a lower storey's main bars project as "starters" into the storey above, the upper column's own main bars lap alongside them for a code-minimum length, and if that overlap is short, missing, or simply never modelled — a starter left stranded after a slab pour, an upper bar begun mid-air with nothing lapped beneath it — the load path the drawing implies does not exist in the model, and today nothing in this repo would ever say so. The team has already named this exact gap in its own words and left it unaddressed on purpose: `RC Automation.pushbutton/todo-list.md`'s own `SCOPE-4` (`RC Automation.pushbutton/todo-list.md:325-327`) records "laps and starter bars" as "explicitly out of scope and reported as such per column, so nobody mistakes the output for a complete cage" — a deliberate exclusion, not an oversight, and one that survives even for columns RC Automation itself places, let alone the far larger share of a project's cages a modeler builds by hand. The closest thing to a check today, `anongee_toolkit.rc_automation.validation`, only ever runs on the Excel workbook before a transaction opens — its cover/spacing/cage-fit checks explicitly disclaim being "sanity limits, not code compliance" and never touch a single placed `Rebar` element — so a modeler working outside the Excel/bridge pipeline gets none of it, and even an RC-Automation-built model only ever had its spreadsheet checked, never its final geometry. The already-logged Column Stack Auditor idea checks the concrete columns' own verticality and never opens a single rebar; this starts exactly where that stops. On the market, reading a model's own placed reinforcement and flagging short or absent lap splices exists only inside paid rebar-detailing/QA modules bundled into full BIM-coordination suites (AGACAD's RC tools, BIM One's rebar QA add-ins, Tekla-class detailing software, all priced per seat); Revit's Review Warnings never inspects lap continuity at all, and nothing free reads a `Rebar` element's own geometry against its neighbour's to say whether two bars actually overlap by the required length.

**Description:**
`Lap & Starter Auditor.pushbutton` (new tool in `Essential.panel/StrucBIM.stack`, sibling to `RoundElementDist.pushbutton` and the logged Column Stack Auditor — a QA tool in the same "check first, never write" family) runs in one window:

2. **Read every placed main bar and its host** — reuses `read_bars()`/`_collect_rebars()` (`rebar_reader.py:115-266`) filtered to bars whose `_host_member_type()` (`rebar_reader.py:68-83`) resolves to a Structural Column, keeping each bar's diameter (the same `REBAR_BAR_DIAMETER` read `rebar_types.bar_diameter_mm()` already performs) and its top/bottom elevation and plan position, extracted with the bounding-box-to-mm pattern `rebar_hosts`'s own elevation/origin helpers already prove, applied to the bar instead of the host.

**Idea name:** Dimension Sweep — whole-view, chained dimension-string batching built directly on AutoDIM's own per-element engine

**Potential:**
`AutoDIM.pushbutton` already solves the hard geometry problem of reading an element's own extents along whichever of its axes lie in the current view plane (`element_frame`/`planar_faces`/`extreme_faces`/`extent_along`, `script.py:69-143`) and placing a clean, correctly-offset dimension off them (`dimension_element`, `script.py:183-237`), but `main()` only ever acts on `revit.get_selection()` (`script.py:312`) — a modeler has to manually multi-select every column, wall and beam that needs a dimension, run the tool, then reselect the next group and run it again, bay by bay and row by row, for the same 40-150-element plan the already-logged Bay Fill idea calls out for slab placement — the identical "click through every instance by hand" tax, just spent on annotation instead of modeling. Worse, every dimension `AutoDIM` places is scoped to exactly what got selected: `dimension_element()` draws one float dimension across a single element's own faces, and `dimension_datums()` (`script.py:254-302`) chains a dimension between whatever 2+ grids/levels happen to be in that one selection — neither ever builds the object a structural plan actually needs, a single continuous dimension **string** referencing every column centerline along one shared grid line in one `ReferenceArray`, ordered end to end; that requires re-selecting and re-running per row today, and nothing assembles the row automatically. `RoundElementDist.pushbutton` already proves the missing piece exists half-built next door — `build_direction_groups(elements, tol)` (`script.py:169-201`) already clusters walls/columns into rows sharing one axis/angle, and `place_dimension()` (`script.py:683-701`) already builds a `ReferenceArray` + `doc.Create.NewDimension` off it — but only ever between exactly **two** elements (a datum and one target), for its own "does this element sit where the datum says" QA job; it stops one reference short of chaining a whole row. And neither tool checks what is already on the sheet: both `dimension_element()`'s and `dimension_datums()`'s `doc.Create.NewDimension` calls (`script.py:232`, `script.py:299`) fire unconditionally, so re-running `AutoDIM` on a row after a later revision (two columns added, one resized) stacks a second dimension line under the first instead of updating it, leaving exactly the kind of duplicate annotation clutter the already-logged Warning Auditor idea's "exact-duplicate instances" fix category exists to catch for model elements — but that idea's `doc.GetWarnings()` scan never looks at `Dimension` elements at all. On the market, "select everything, one dimension string per row, auto" is sold only as a bundled feature inside paid drafting-automation add-ins (CTC's dimensioning tools, BIM One's auto-dimension utilities, assorted Autodesk App Store add-ins priced per seat); Revit's own multi-pick dimension tool still requires picking every reference by hand, and nothing free reads a plan's own column/wall/framing rows and grid lines and strings them in one batched pass.

**Description:**
`Dimension Sweep.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `AutoDIM.pushbutton` — this calls AutoDIM's own engine rather than re-implementing it) runs in one window:

1. **Scope & categories** — active view only (dimensions are view-specific, same constraint `AutoDIM` already enforces via `_NO_DIM_VIEWS`, `script.py:34-37`), tick which categories to sweep: Structural Columns, Structural Framing, Walls, and/or Grids/Levels — no selection needed, the whole point being to replace `revit.get_selection()` with a full collector.
2. **Cluster into rows** — every ticked element collected via `FilteredElementCollector(doc, active_view.Id)`, then bucketed by shared axis/angle using `build_direction_groups()` lifted out of `RoundElementDist.pushbutton` (same clustering, second caller — the same "one function, two callers" promotion the already-logged Grid Mark Assistant idea proposes for that tool's `_distance_to_line`); grids/levels cluster the same way `dimension_datums()` already groups a manual selection, just run across every datum in the view instead of only a chosen few.
3. **Build one chained string per row** — the genuinely new piece: for a column/wall/framing row, every member's extreme-face reference (from `AutoDIM`'s own `planar_faces()`/`extreme_faces()`, unmodified) is collected into one `ReferenceArray` ordered by position along the row's axis and fed to a single `doc.Create.NewDimension` — one continuous string, not `dimension_element()`'s N isolated per-element floats; a grid/level row calls `dimension_datums()` exactly as it exists today, unchanged.
4. **Duplicate-run guard** — the other genuinely new piece neither source tool has: before building anything, `FilteredElementCollector(doc, active_view.Id).OfClass(DB.Dimension)` is read and each existing dimension's `.References` compared against a row's computed reference set; a row whose references are already fully covered by one existing dimension is marked **already dimensioned** and skipped by default, and a row that's a superset of an existing dimension's references (new columns added to an existing row since the last sweep) is marked **row changed — will replace**, so a re-run after a revision only ever adds or refreshes what actually changed instead of stacking a second string under the first.
5. **Preview checklist** (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`, the same shell `ConvertFloor.pushbutton` and `AutoDIM`'s proposed siblings already run on) — one row per detected chain: category, member count, axis, and status (**will place** / **already dimensioned** / **row changed — will replace** / **blocked**, with the exact block reason `dimension_element()` already returns — "no planar faces", "no element axis lies in the view plane", etc., `script.py:186-194` — surfaced per member instead of silently dropped), plus a **Locate** action per row that isolates the row's members in the view.
6. **Place** — one `Transaction`; a "row changed" row deletes its stale dimension (`doc.Delete`) before creating the replacement, everything else creates fresh; one bad row's reference failure rolls back only that row, the rest of the sweep continues.
7. **Report** — placed / replaced / skipped-already-dimensioned / blocked counts, with the block reasons grouped the same way `AutoDIM`'s own `main()` already prints per-note today (`script.py:338-339`), just rolled into one run summary instead of one console line per manual selection.

**Implementation:**
- Promote `AutoDIM.pushbutton`'s `element_frame`, `planar_faces`, `extreme_faces`, `extent_along`, `classify` and `dimension_element` (`script.py:69-237`) into a shared `anongee_toolkit.revit.dimensioning` module so both the existing single-selection tool and this new sweep call one copy instead of a second implementation of the same face-reading math; `AutoDIM.pushbutton/script.py` becomes a thin caller of the promoted module, behaviour unchanged.

4. One `TransactionGroup`, one `Transaction` per element — a single failure rolls back only that element.
5. Result table with a geometry delta (footprint area / volume / centroid) per element, flagged the same way `Convert Slab` flags a delta over tolerance.

What survives: level + base/top offset, structural flag, phase, workset, pin state, all writable instance + shared parameters matched by BuiltInParameter → shared GUID → name (unmatched ones listed by name), joins and join order (recorded, re-applied via `SwitchJoinOrder`), and — the hard part that makes this worth building rather than hand-converting — **hosted rebar re-pointed to the new host** via `Rebar.SetHostId` before the original is deleted, exactly like `Convert Slab` already does for slab-hosted rebar. What's lost, reported per element for confirmation: tags, dimensions, face-hosted family instances (door/window openings on a converted wall have nowhere to go on a column and vice versa), parts, the ElementId itself.

**Implementation:**
- Fork `ConvertFloor.pushbutton/script.py` structurally rather than the code: same recreate → replay → delete → rejoin → rehost-rebar → verify pipeline, same `type_name_mode` (`"same"` 1:1 by name, `"convention"` prefix/suffix + dimension-tolerance matching), same model-group ungroup/convert/regroup handling for single-instance groups, same blocked-by-default posture for multi-instance groups and elements in assemblies/inactive design options.
- New geometry step neither existing tool needs: footprint → line+thickness resolution for Column→Wall (via the column's `BoundingBoxXYZ` / cross-section sketch, falling back to the family's cross-section parameters when available) and line+thickness → footprint for Wall→Column — this is the one genuinely new piece of logic; everything else (parameter carry-over, join preservation, group handling, checklist UX, transaction-per-element rollback) is lifted from `ConvertFloor.pushbutton` and `anongee_toolkit.ui`.
- Rebar rehost reuses the exact `Rebar.SetHostId` call already proven in `ConvertFloor.pushbutton`; the "what's lost" report reuses its `forms.confirm` gate naming every element whose dependents will be destroyed.
- New `column_wall_convert_config.json` alongside `script.py`, mirroring `slab_convert_config.json`'s shape (`type_name_mode`, `thickness_tolerance_mm`, `groups.multi_instance`, plus a new `wall_axis_mode: "long_side" | "prompt"` and `column_spacing_mm` for the wall→column split case).
- Sits in `Essential.panel/StrucBIM.stack/`, next to `Convert Slab.pushbutton`, using the same `bundle.yaml` / `README.md` / `CHANGELOG.md` layout the root README documents for versioned tools.

**Future update:**
- Extend the footprint resolver to L/T-shaped and round columns by decomposing into multiple straight wall segments instead of blocking outright.
- Wall→Column mode learns a "replace every column-spaced stretch of this wall" batch mode, for converting an entire shear-wall run back into a column-and-infill scheme in one pick.

## 2026-09-11 14:30 UTC

**Idea name:** Universal Renamer — token templates + Excel mapping, across every renameable category

**Potential:**
Renaming to match a client's naming standard is one of the most repeated, most tedious tasks on a BIM team, and today it's done by hand, category by category, inside dialog boxes that only support simple find/replace. A model handover or a mid-project standard change (new discipline codes, new level naming, a merged project) can mean renaming 100+ sheets, views, levels, grids and schedules by hand — normally a half-day to a full day of pure clicking, with the real risk of dropped titleblock/view sync errors along the way. A token-driven, previewed, one-batch rename collapses that to minutes and removes the manual-error risk entirely. This is squarely in the productivity bracket the team already values enough to have built **Bulk Rename** for — it just stops short of the categories modelers actually rename most.

**Description:**
`Universal Rename.pushbutton` (or a new `Universal Rename.pulldown` sibling to the existing `Bulk Rename.pulldown`) extends renaming beyond Fill Patterns / Line Patterns / Line Styles to the categories a BIM modeler renames every week:

- Views (all types) and Sheets
- Levels and Grids
- Schedules and View Filters
- Family Types (within a family, e.g. duplicating a type-catalog row)

Two rename modes, selectable per run:
1. **Token template** — build a pattern from live tokens (`{Discipline}`, `{Level}`, `{ViewType}`, `{SheetNumber}`, `{OldName}`, `{Index:03}`, a regex capture group from the current name) and apply it across every selected/filtered element in one pass, e.g. turn `S-101 - Foundation Plan` into `STR-L00-FOUNDATION-PLAN`.
2. **Excel mapping** — drop in a two-column workbook (`Old Name → New Name`), matched by exact name or regex; this is the fast path for a client-supplied rename schedule that already exists as a spreadsheet, and it's fully auditable (the workbook itself is the change record).

Both modes share one pipeline: filter (by category, by naming pattern, by pre-selection) → live preview table showing old name / new name / collision flags → user unticks anything wrong → single `Transaction`, one undo step → result report (renamed / skipped / collided), exportable back to Excel for a handover record.

**Implementation:**
- Reuse the existing `Bulk Rename.pulldown` engine (`AnonGee.extension/AnonGee.tab/Essential.panel/Bulk Tool.stack/Bulk Rename.pulldown/`) as the base: it already has the search/tick/apply/report loop for style-type elements — generalize its element-fetch + rename-call layer behind a small per-category adapter (`views.py`, `sheets.py`, `levels.py`, `grids.py`, `schedules.py`, `filters.py`, `family_types.py`), each just implementing "list renameable items" + "apply new name" + "collision check", same shape `ConvertFloor.pushbutton` uses for its own per-category resolution.
- Token engine: small formatter over Revit's built-in parameters + regex capture groups pulled from the current name (`re.match` against a user-supplied pattern) — no new dependency, CPython3 stdlib `re` is enough.
- Excel mapping: reuse the `openpyxl` path already proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton` for read + the write-back report.
- Collision detection before the transaction opens (duplicate target names within the batch, or a target name already used elsewhere in the model) — block those rows, same "blocked rows pre-unticked" UX `Convert Slab` uses.
- Sits as a new pulldown/stack entry in `Essential.panel/Bulk Tool.stack/`, next to `Bulk Rename.pulldown`, following the same `bundle.yaml` / `ui.xaml` / `script.py` bundle layout documented in the root README.
- Ships with its own `CHANGELOG.md` since it's a tool likely to grow new categories over time (same pattern as `AutoLevel.pushbutton`).

**Future update:**
- Saved rename profiles (per-client naming standard), reusable across projects — analogous to Filter View Manager's project/workstation rule store.
- Extend token source to shared parameters, not just built-ins, so a firm-specific "Discipline Code" parameter can drive the template directly.
- Batch rename across a set of linked/worksharing-central models in one run (multi-document mode), for firms that split a project into linked structural/architectural/MEP files with a shared naming standard.

## 2026-09-15 10:41 UTC

**Idea name:** Bulk Purge — unused View Templates, Filters & Materials, with a live usage-count column (grows `Bulk Delete.pulldown` past styles-only)

**Potential:**
Revit's own **Manage → Purge Unused** stops at zero-instance family types and a short fixed list of style categories — it has never touched View Templates, Filters or Materials, because none of those are ever "in use" in the instance-count sense Purge Unused checks; a View Template with zero views assigned, a Filter added to no view's V/G list, a Material referenced by no compound-structure layer or paint override just sit there forever. On a project handed between modelers, copy-pasted from an old template file, or accumulated over a multi-phase job, this is routinely 30-80 dead View Templates and Filters and a couple dozen dead Materials by the time of handover — and today the only way to find them is opening **Manage → View Templates** / the Filters tab in Visibility Graphics / the Material Browser and eyeballing each one, with no usage count shown anywhere in Revit's own UI, so a modeler either leaves them (file bloat, a Type Selector and filter-picker cluttered with dead entries) or deletes on a guess and risks silently un-assigning a template or filter that actually was in use on a view nobody checked. This repo already solved exactly this shape of problem for three narrower categories — `Bulk Delete.pulldown`'s `Delete FillPatterns.pushbutton` / `Delete LinePatterns.pushbutton` / `Delete LineStyles.pushbutton` — but all three list *every* fill pattern / line pattern / line style with no usage information at all and rely on `doc.Delete()` silently failing on an in-use one (`Delete FillPatterns.pushbutton/script.py:242-249`, `"except Exception: skipped += 1   # system-locked / in-use"`), which works only because a fill/line pattern still in use is safe to leave untouched by a failed delete — a View Template still assigned to views or a Filter still in a view's filter list is not the same case: deleting either one *succeeds* and silently strips the assignment from every view carrying it, so the exact "list everything, try delete, skip failures" shape this repo already ships would quietly break views if pointed at these three categories unchanged. That gap — no usage-count anywhere in Revit's UI, and this repo's own working pattern being unsafe to reuse as-is for these categories — is what makes this worth building rather than just adding three rows to an existing dropdown. On the market, whole-model cleanup of unused View Templates/Filters/Materials in one pass is sold only as a "purge/clean-up" line item inside paid whole-project add-ins (Ideate Sidekick's Purge, BIM One's eTools-class utilities), licensed per seat as part of a much larger bundle; nothing free computes a per-item usage count for these three categories at all, Revit's own Purge Unused included.

**Description:**
Three new pushbuttons — `Delete View Templates.pushbutton`, `Delete Filters.pushbutton`, `Delete Materials.pushbutton` — added to the existing `Bulk Delete.pulldown` (`AnonGee.tab/Essential.panel/Bulk Tool.stack/Bulk Delete.pulldown/`), same search-box / checklist / Select-All-Select-None / live-count / delete-with-confirm shell as the three style-deletion buttons already there, with one addition every existing one is missing: a **usage-count badge per row** ("used by 0 views", "used by 12 views", "used by 3 types"), computed up front and never guessed at.

1. **Collect + count** — per category:
   - *View Templates:* every `View` where `IsTemplate` is true; usage count = how many non-template views in the model have `ViewTemplateId` equal to it.
   - *Filters:* every `ParameterFilterElement`; usage count = how many views return it from `GetFilters()`.
   - *Materials:* every `Material`; usage count = how many loaded types reference it in a `CompoundStructure` layer (paint-override references are a known gap, named explicitly in the dialog rather than silently missed — see Implementation).
2. **Sort and pre-tick by usage** — zero-usage rows sort to the top and are pre-ticked (this is the "safe, opt-out" purge case); any row with usage_count > 0 starts unticked, and ticking one changes the confirm-dialog wording to name exactly what breaks ("2 of the items you picked are still in use — deleting them will silently un-assign the View Template from 5 views / drop the Filter from 3 views' filter lists").
3. **Search + Select-All/None** — identical to the existing three buttons, operating only on the currently-visible (search-filtered) rows, same as `Delete FillPatterns.pushbutton/script.py`'s `_on_all`/`_on_none`.
4. **Delete** — one `Transaction`, same per-item try/skip loop the existing three buttons already use, since a genuinely-in-use element (a Material still painted onto a face, for instance) can still fail to delete and should be skipped rather than blocking the batch.
5. **Result** — "Deleted N of M (K skipped — still referenced)" exactly matching the existing message shape, so the three new buttons read as siblings of the three that already exist rather than a different tool bolted on.

**Implementation:**
- Add three entries to the `_PROVIDERS` dict in the shared engine, `anongee_toolkit/operations/bulk_delete.py:64-83`, alongside the existing `fillpattern` / `linepattern` / `linestyle` keys — `viewtemplate`, `filter`, `material` — each supplying a `collect(doc)` that returns `[(name, ElementId, usage_count)]`, a 3-tuple where today's collectors (`_collect_fillpatterns`/`_collect_linepatterns`/`_collect_linestyles`, `bulk_delete.py:34-57`) return a 2-tuple; `GenericBulkDeleteDialog._rebuild_list()` (`bulk_delete.py:161-174`) needs the extra field threaded through to a new usage-badge `TextBlock` next to each row's name, and `_on_delete`'s confirm prompt (`bulk_delete.py:213-215`) needs the in-use-row count spliced into its wording.
- `_collect_view_templates(doc)`: `FilteredElementCollector(doc).OfClass(View)` filtered to `.IsTemplate`; usage count via a single pass over every non-template view's `ViewTemplateId` (the exact property already read one-view-at-a-time in `ToggleLinked.pushbutton/script.py:16,43` and `AutoLevel.pushbutton/anongee_autolevel/revit_ops.py:492` — this is its first aggregate, whole-model use).
- `_collect_filters(doc)`: `FilteredElementCollector(doc).OfClass(ParameterFilterElement)`; usage count via `view.GetFilters()` per eligible view — a call that returns **zero hits anywhere in this repo today** (confirmed by grepping every `script.py` and every `anongee_toolkit` module for `GetFilters`), the closest existing code being `cad2bim/builders/view_filters.py:170-171`'s `AddFilter`, a write-only, create-time call that has never been paired with a read.
- `_collect_materials(doc)`: `FilteredElementCollector(doc).OfClass(Material)` — the same collector `cad2bim/builders/materials.py:75` already runs, there purely to create materials during a CAD import, never to count usage; usage count from `FilteredElementCollector(doc).OfClass(FloorType/WallType/...)`'s `GetCompoundStructure().GetLayers()` matched by `MaterialId`. Paint-override usage (`doc.Settings`/`Document.GetPaintedFaces`-style lookups) is left out of v1 and the dialog says so in its info badge, rather than reporting a false zero-usage count for a material that's actually painted onto a face somewhere.
- New `ui.xaml` row template: reuses the existing `ItemsList`/`ListBoxItem`/`CheckBox` shape verbatim (`Delete FillPatterns.pushbutton/ui.xaml`) with one added `TextBlock` bound to the usage-count string, styled with the same inlined theme resources already duplicated across all three existing `ui.xaml` files.
- The three new pushbuttons import `GenericBulkDeleteDialog` from `anongee_toolkit.operations.bulk_delete` directly — the first production caller of that shared module: today all three existing Bulk Delete pushbuttons (`Delete FillPatterns.pushbutton/script.py`, and its LinePatterns/LineStyles siblings) each carry their own fully inlined copy of the same dialog class and `PROVIDERS` dict rather than importing the shared one (confirmed: no `AnonGee.tab/**/script.py` imports `anongee_toolkit.operations.bulk_delete`), so this closes that three-way duplication as a side effect of adding the new categories on top of the shared engine instead of a fourth inline copy.
- Sits as three more pushbuttons inside the existing `Bulk Delete.pulldown/bundle.yaml` grouping, no new panel or stack needed.
