## 2026-09-16 00:39 UTC

**Idea name:** Rebar Cover Auditor — whole-model, code-minimum cover check against the actual constrained bar-to-face distance, generalized off RC Automation's own footing-only cover-write path

**Potential:**
Concrete cover is the single reinforcement dimension most likely to be wrong in a hand-detailed or imported model and least likely to be caught before it reaches a drawing: Revit shows a bar's *shape* in every view, but nothing in its own UI reports the actual distance from a bar to the nearest formwork face, and "Edit Constraints → Constrain to Cover" only tells you whether a handle *is* tied to cover, one bar and one handle at a time — there is no whole-model report of what every bar's cover actually resolves to versus what the design intends. On a column-heavy or footing-heavy structural model that's dozens to hundreds of individual bars whose cover only becomes visible when a site engineer complains about a bar showing through formwork or a code-compliance reviewer flags it late, at which point fixing it means re-opening constraints bar by bar. This repo already built the two hard pieces this needs — `anongee_toolkit/structural/rebar_constraints.py`'s `distance_to_cover_mm()`/`describe()` (reads a shape-driven bar's actual signed gap to its constrained cover face, built for a one-off diagnostic dump) and `anongee_toolkit/structural/rebar_factory.py`'s `describe_cover()`/`set_host_cover()` (reads/writes a *host's* declared cover parameters, built only for footings RC Automation itself places) — but both are internal, single-purpose helpers wired only into RC Automation's own footing-placement flow (`RC Automation.pushbutton/script.py:311-327`); neither has ever been exposed as a standalone, whole-model, any-category audit a modeler can run over rebar that RC Automation didn't place — hand-drawn column ties, beam stirrups, slab mesh, or anything inherited from a linked/imported model. On the market, rebar cover checking exists only inside expensive whole-discipline QA suites (Naviate Structure's reinforcement checks, CSI-class rebar detailing add-ins) sold per seat as part of a much larger bundle; nothing free reports a bar's actual geometric cover against a code-minimum table at all.

**Description:**
`Rebar Cover Auditor.pushbutton`, sibling to `Copy Rebar Visibility.pushbutton` / `Obscured Rebar.pushbutton` in `Essential.panel/Bulk Tool.stack/Rebar.pulldown/`, following the same report-first, approve-each-fix posture `Round Element Dist.pushbutton` already established for a different dimension (element-to-datum distance) on the same panel:

1. Collects rebar — pre-selection if there is one, otherwise every `Rebar`/`RebarInSystem` element in the model, grouped by host category (Column, Beam, Foundation, Floor, Wall).
2. For each bar, resolves two numbers: **actual cover** — `distance_to_cover_mm()` per shape-driven handle already tied to a cover face (skipping handles tied to a face, not cover, and free-form bars, both named explicitly as "not checkable this way" rather than silently reported as compliant) — and **required cover** — the host's own declared `CLEAR_COVER_TOP/BOTTOM/OTHER` parameter when set, else a code-minimum looked up by exposure condition and bar diameter from a new minimum-cover table (IS 456:2000 Table 16, ACI 318 Table 20.6.1.3.1, or BS 8500, selected the same way BBS Generator already lets a project pick IS 2502 / BS 8666 / ACI 315).
3. Live table, one row per bar (grouped and collapsible by host element): host, face, actual cover, required cover, delta, status (OK / under / over / unconstrained / no-parameter). Sorted worst-first, same "report every deviation first" framing `Round Element Dist` already uses.
4. Ticked rows only get touched: for a bar whose handle is already constrained to the right face but sitting at the wrong distance, offers to re-run `constrain_to_cover()` against the correct cover type (creating/reusing one via `ensure_cover_type()` exactly as `set_host_cover()` already does for footings); for a bar with no host cover parameter set at all, offers to write it via `set_host_cover()` first. Bars this can't safely auto-fix (free-form geometry, no constraint manager on this Revit build, a handle tied to a face rather than cover) are listed with the reason and left for manual correction — never guessed at.
5. One `Transaction`, undo in one step; result report + Excel export (old/new cover per bar) for a documented QA record, reusing the `openpyxl` write-back path already proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton`.

**Implementation:**
- Read path is almost entirely existing code, just newly exposed at whole-model scope instead of one-bar-at-a-time: `anongee_toolkit/structural/rebar_constraints.py`'s `manager_for()`, `is_shape_driven()`, `handles()`, `distance_to_cover_mm()` and `target_face()` (today only reachable through `describe()`'s single-rebar diagnostic string) become the per-bar data source; `anongee_toolkit/structural/rebar_factory.py`'s `describe_cover()` supplies which cover parameter each host actually exposes.
- Fix path reuses `rebar_factory.ensure_cover_type()` (cache-keyed by face+value, exactly as documented against the three-duplicate-type bug it already fixed for RC Automation) and `rebar_constraints.constrain_to_cover()` for the "re-tie to correct cover" action, and `rebar_factory.set_host_cover()` for the "host has no cover parameter yet" action — all three called today only from inside RC Automation's footing-placement transaction, none from a UI a modeler drives directly.
- New piece this needs that nothing in the repo has today: a minimum-cover-by-exposure table, `standards/cover_minimums.py` (one per code, mirroring the `standards/IS_2502_2019.py` / `BS_8666_2020.py` / `ACI_315_2018.py` layout BBS Generator already uses for bending tables) keyed by exposure class and bar diameter, used only as the fallback when a host has no explicit cover parameter set.
- UI: a grouped, sortable results table matching `Round Element Dist`'s worst-first / tick-to-fix / skip-with-reason shell, reusing the shared WPF `Controls.xaml`/`Panels.xaml` theme every other tool already draws from.
- Sits in `Essential.panel/Bulk Tool.stack/Rebar.pulldown/`, next to `Obscured Rebar.pushbutton` and `Copy Rebar Visibility.pushbutton`, same `bundle.yaml`/`README.md`/`CHANGELOG.md` layout the root README documents for versioned tools.

**Future update:**
- Extend the exposure-condition lookup to read a project parameter (e.g. "Exposure Class") per host instead of one project-wide setting, for a model mixing footings (severe exposure) and internal columns (mild exposure).
- Add clear bar-to-bar spacing (not just cover-to-face) as a second check column, using the same per-handle geometry once cover is proven in production.
- Feed the "no cover parameter set" list into `Parameter Combination`/the filter-parameter tools as a one-click batch-set action across every host sharing a type, instead of one host at a time.
- A combined structural QA dashboard alongside the already-logged Lap & Starter-Bar Continuity Auditor and Column Stack Auditor, one pass over the whole rebar model with one summary report.

## 2026-09-15 15:40 UTC

**Idea name:** Sheet Issue Kit — one-click PDF + DWG + NWC export of a rule-picked sheet set, token-named, with a since-last-run diff so a re-issue only touches what actually changed

**Potential:**
Every drawing issue — a weekly coordination set, a milestone submission, a tender package — repeats the same non-modelling admin for every sheet in scope: open Revit's PDF export dialog, hand-pick or reuse a saved sheet set, set naming, export; reopen the completely separate DWG export dialog, re-pick the same sheets (its own naming options don't match the PDF dialog's), export; if Navisworks coordination is also owed, a third dialog, a third naming pass — three independent settings screens, repeated in full for every issue, even when only three of forty sheets actually changed since last week. Nothing in this repo touches this at all: grepping every script under `AnonGee.tab` and every module under `anongee_toolkit` for `PDFExportOptions`, `DWGExportOptions`, `ExportOptions`, `ViewSheetSet`, `PrintRange`, `IPrintSetup`/`GetPrintSetup` and `ExportImage` returns zero Revit API hits anywhere in the codebase (the `pythonwin`/`ezdxf` vendored-library hits for `printRange`/`.print()` are unrelated MFC/CLI code, not Revit). The one place "PDF" appears at all, `Export Schedule.pushbutton`'s `ChkSavePdf` checkbox (`script.py:309,421`) feeding `_excel_polish(xlsx_path, want_pdf)` (`script.py:669-732`), is a different job entirely: it drives **Excel COM** (`xlTypePDF`, `script.py:728`) to print the *just-exported .xlsx workbook* to PDF, degrading gracefully when Excel isn't installed (`script.py:673`, "degrades gracefully without Excel") — it never calls `Document.Export`, never touches a `View`/`ViewSheet`, and has nothing to do with issuing drawing sheets. The view-enumeration helper that exists, `anongee_toolkit.revit.views.get_eligible_views()`/`ALLOWED_VIEW_TYPES` (`revit/views.py:9-17,35-56`), explicitly excludes `ViewSheet` from its allowed set — built for element-visibility tools, not sheet issuance — so it cannot be reused here as-is. The only code that reads a sheet's own `SheetNumber`/`Name` at all is `anongee_toolkit.structural.inventory._views()` (`structural/inventory.py:323-341`), and only as one read-only field in `Extract Template.pushbutton`'s audit report — never as a live, selectable list, and never combined with a titleblock read for per-sheet paper size. Revit's own `Revision`/issue-date concept (`ViewSheet.GetCurrentRevision`, `SHEET_ISSUE_DATE`) is likewise never read anywhere in the repo; the only "revision" in the codebase is `BBS Generator.pushbutton`'s own unrelated Excel-sidecar diff (`chk_revision`/`tb_revision`, `ui/main_window.py:193-200,423-434`), which tracks bar-list changes between two spreadsheet snapshots, not a sheet's Revit revision. Revit's native PDF/DWG exporters can already batch off a manually pre-built, saved `ViewSheetSet` element, but that native path still forces three separate dialogs (PDF, DWG, and — if owed — a fourth-party Navisworks exporter) with three independent, non-token, non-parameter-aware naming schemes reconfigured by hand on every single issue, and it has no concept of "only the sheets that changed since the set was last issued" — every run re-exports the whole set regardless of what actually moved. On the market, wrapping the native exporter in a single multi-format pass with templated file names is exactly the headline feature CTC's BIM Tools, Ideate Sheets/BIMLink, and IMAGINiT Clarity sell as one line item of a much larger paid, per-seat suite; none of them — free or paid — skip re-exporting an unchanged sheet on a re-issue.

**Description:**
`Sheet Issue Kit.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `Export Schedule.pushbutton` and forking that tool's `ExportScheduleDialog` shell — search box, checklist, badge triplet — for sheets instead of schedules) runs in one window:

1. **Sheet list** — every `ViewSheet` in the model (`FilteredElementCollector(doc).OfClass(ViewSheet)`, the same collector `structural.inventory._views()` already proves at `inventory.py:337`, promoted from a read-only audit field to a live, checkable list), shown with the same search-and-checkbox `ListBoxItem` pattern `ExportScheduleDialog._populate`/`_on_search_changed` already build (`Export Schedule.pushbutton/script.py:329-359`), all ticked by default.
2. **Filter to scope, not just tick by hand** — an optional rule row (parameter + value: discipline, a sheet-list "Revision" text parameter, a Yes/No "Issue" checkbox parameter, or a saved Revit `ViewSheetSet` name if one already exists) that pre-ticks the matching subset via `anongee_toolkit.revit.parameters.get_parameter_value` (`revit/parameters.py:36-82`) — the same read function the already-logged Schedule Round-Trip and Parameter Migrator ideas both call, this becomes a further caller — so a "just the structural set" or "just what's marked Issue = Yes" re-issue doesn't require re-hand-picking sheets from a 200-sheet list every week.
3. **Since-last-run diff** — the genuinely new piece nothing in the repo or, as far as this codebase's own market research shows, any competing add-in does: a small per-project sidecar JSON (`sheet_issue_kit_log.json`, alongside the model, one entry per sheet keyed by `ElementId` storing the sheet's content-hash — every placed view's `ElementId` + last-changed `Element.UniqueId`/`Document.GetElement(id).VersionNumber` pairing already exposed by the Revit API — and the export timestamp) is diffed against the current model on open; each ticked sheet shows **unchanged since last issue** or **changed — will export**, with a one-click "export everything anyway" override, so a Friday re-issue after three sheets changed doesn't silently regenerate all forty.
4. **Formats** — independently toggleable PDF / DWG / NWC checkboxes; PDF via `Document.Export(folder, name, ViewSet, PDFExportOptions)`, DWG via `Document.Export(folder, name, viewIds, DWGExportOptions)`, NWC via the Navisworks exporter's `NavisworksExportOptions` when that add-in is installed — detected once at startup and the NWC checkbox disabled with an inline reason rather than failing mid-run if it isn't, the same "degrade, don't crash" posture `Export Schedule.pushbutton`'s own Excel-COM absence handling already proves (`script.py:673`).
5. **File naming** — a token template (`{SheetNumber}_{SheetName}_{Revision}_{Date}`) applied per sheet per format, reusing the token formatter the already-logged Universal Renamer idea proposes if that tool has landed by the time this one is built, otherwise a small standalone `re`-based formatter promoted into the shared one the moment Universal Renamer exists — the same fallback posture the already-logged Sheet Set Builder idea commits to for its own naming step.
6. **Preview checklist** (`anongee_toolkit.ui.checklist.CheckList`, the shell every other batch tool in the repo already runs on) — one row per (sheet, format): resolved file name, size/scale read off the sheet's own titleblock via `structural.inventory._views()`'s existing title-block enumeration (`inventory.py:343-...`), and status (**will export** / **unchanged — skip** / **blocked — NWC exporter not installed**).
7. **Export** — one pass through the ticked rows per format, each format's own `ExportOptions` object built once and reused across every sheet in that format rather than reconstructed per sheet; a single bad sheet (a corrupt titleblock, a locked output path) is caught and reported without aborting the rest of the run.
8. **Report** — exported / skipped-unchanged / blocked counts per format, the sidecar log updated for every sheet actually exported, and an `openpyxl` issue-record (reusing the styling constants `Export Schedule.pushbutton` already proves, `script.py:148-161`) naming exactly what went out in this issue — the artifact a modeler currently has to build by hand for a transmittal record.

**Implementation:**
- New `anongee_toolkit.revit.sheet_export` module — the genuinely new piece, since no `PDFExportOptions`/`DWGExportOptions`/`ViewSheetSet` call exists anywhere in the toolkit today (confirmed by the repo-wide grep above): one function per format wrapping `Document.Export`, and one `NavisworksExportOptions` probe that returns `None` rather than raising when the Navisworks exporter isn't installed.
- Sheet enumeration goes straight through the same `FilteredElementCollector(doc).OfClass(ViewSheet)` collector `structural.inventory._views()` (`inventory.py:337`) already proves, rather than a second hand-rolled collector; titleblock size/scale reuses that same function's title-block read (`inventory.py:343-...`).
- Parameter-rule filtering and diff-detection both go through `anongee_toolkit.revit.parameters.get_parameter_value` (`revit/parameters.py:36-82`), the same read function the already-logged Schedule Round-Trip and Parameter Migrator ideas call — no second parameter-read convention introduced.
- UI shell is a direct fork of `ExportScheduleDialog` (`Export Schedule.pushbutton/script.py:281-360`) — same `XamlReader.Load`, search box, badge triplet — with the schedule checklist swapped for a sheet checklist and one added filter-rule row.
- `sheet_issue_kit_config.json` alongside `script.py` (default naming template, default rule parameter name, which formats default-on, sidecar log path), mirroring `slab_convert_config.json`'s override-by-config shape every other configurable tool in the repo already uses.
- Excel issue-record export reuses the `openpyxl` path and brand constants already proven in `Export Schedule.pushbutton` (`script.py:148-161,455-...`).
- Sits in `Essential.panel/Action.stack/`, next to `Export Schedule.pushbutton`, its direct sibling and the tool it forks its dialog shell from.

**Future update:**
- Read a project's actual `ViewSheetSet` elements (if any already exist) as a fourth filter option alongside the parameter rule, so a firm that already maintains named sheet sets in-model doesn't have to re-express that grouping as a parameter rule.
- Feed the sidecar diff log into a "what changed since last issue" summary view, similar in spirit to the already-logged Warning Auditor and Dimension Sweep ideas' own re-run/diff modes, so a coordination meeting can open with "these six sheets moved since Tuesday" instead of a modeler reconstructing that by memory.
- Batched combined-PDF output (one file for the whole set, Revit's own "combine into one file" PDF option) as a togglable alternative to one-file-per-sheet, for submissions that want a single transmittal PDF rather than a folder of them.
- Tie the token naming template to the same shared formatter the already-logged Universal Renamer and Sheet Set Builder ideas both plan to converge on, so all three tools stop carrying independent standalone fallback formatters the moment one of them lands first.

## 2026-09-15 05:39 UTC

**Idea name:** View Graphics Sync — one-view-to-many propagation of category overrides, filters, view range and worksets, generalized off Copy Rebar Visibility's own narrow element-hide engine

**Potential:**
Getting a set of similar views to look consistent — every structural framing plan carrying the same category overrides, the same filter list with the same colours and the same enabled state, the same view range, the same workset visibility — is one of the most repeated setup chores on a BIM team, and today this repo gives a modeler exactly one narrow tool for it: `Copy Rebar Visibility.pushbutton` copies hide/unhide state plus the `Unobscured`/`Solid` flags, but only for `OST_Rebar` (`Copy Rebar Visibility.pushbutton/script.py:274-279` collects `FilteredElementCollector(doc).OfCategory(BuiltInCategory.OST_Rebar)` — nothing else). Everything past that is manual, view by view: category graphic overrides (line colour/weight, surface pattern, halftone, transparency), the filter list and each filter's own override + enabled flag, view range, and workset visibility have no copy-between-views tool anywhere in this codebase — confirmed by grepping every script under `AnonGee.tab` and every module under `anongee_toolkit` for `SetCategoryOverrides`, `GetCategoryOverrides`, `SetFilterOverrides`, `IsFilterEnabled`, `GetViewRange`, `SetViewRange` and `SetWorksetVisibility`: `SetFilterOverrides`/`AddFilter` turn up exactly once, in `anongee_toolkit/cad2bim/builders/view_filters.py:170-171`, and only as a **write** the first time a filter is created on every *open* view (`view_filters.py`'s own docstring: "applied to every OPEN view in the document") — never read from one view and replicated onto a chosen target set; `GetCategoryOverrides`/`SetCategoryOverrides`, `GetViewRange`/`SetViewRange` and `SetWorksetVisibility` return **zero hits anywhere in the repo**. The one related precedent, `ToggleLinked.pushbutton`, only flips a single category's (`OST_RvtLinks`) hidden flag on the active view and already had to solve the "a view template is silently blocking this" problem once (`template_controls_links`/`release_links_from_template`, `ToggleLinked.pushbutton/script.py:14-33`, keyed to `BuiltInParameter.VIS_GRAPHICS_RVT_LINKS`) — that per-parameter template-override check has never been generalized past that one link-visibility parameter. Revit's own native answer is View Templates, but a template is all-or-nothing per parameter and project-wide by design; it cannot selectively push "just these three filters, as they are right now on this one cleaned-up view" onto eleven others without either forcing every one of them onto a template (dragging in every *other* template-controlled setting too) or hand-replicating the change eleven times — 10–20 minutes per view for a non-trivial override set, redone every time a new plan is duplicated mid-project. On the market this exact "view A's graphics → views B, C, D" copy is sold only bundled inside large paid production suites (CTC BIM Tools, IMAGINiT Utilities) as one line item of a much bigger licensed toolset; nothing free does a direct, selective, view-to-view graphics copy outside of template assignment.

**Description:**
`View Graphics Sync.pushbutton` (new sibling to `Copy Rebar Visibility.pushbutton` in `Bulk Tool.stack`, reusing that tool's own source-combo / target-checklist window shell) runs in one pass:

1. **Pick the source view** — a ComboBox of every eligible view (same `ALLOWED_VIEW_TYPES` set `Copy Rebar Visibility.pushbutton/script.py:39-46` already defines: floor/ceiling/structural plan, section, elevation, 3D), defaulting to the active view exactly like the rebar tool already does (`script.py:117-123`).
2. **Pick the target views** — the same `CheckBox`-per-`ListBoxItem` multi-select list (`script.py:125-134`), built from `anongee_toolkit.revit.views.get_eligible_views()` (`revit/views.py:30-56`) instead of a hand-rolled collector, so this becomes that helper's second real caller.
3. **Choose which property groups to sync**, each independently toggleable so a modeler who only wants filters fixed isn't forced to also touch view range: Category visibility + graphic overrides (line colour/weight/pattern, surface pattern, halftone, transparency — every category the source view actually overrides, read via `View.GetCategoryOverrides`/hidden state via `GetCategoryHidden`, generalizing `ToggleLinked.pushbutton`'s single-category `SetCategoryHidden` call to every category the source touches); Filters (the source view's own filter list plus each filter's override settings and enabled/visible flag, added to a target view via `AddFilter`/`SetFilterOverrides` the same way `cad2bim/builders/view_filters.py:170-171` already creates them, but read from an existing view instead of freshly authored); View Range (plan-type views only, via `GetViewRange`/`SetViewRange`); Workset visibility (`SetWorksetVisibility` per workset).
4. **Template-lock detection per (view, property)** — before anything is queued, checks whether a target view's `ViewTemplateId` controls the parameter in question, reusing `ToggleLinked.pushbutton`'s own `template_controls_links` pattern (`script.py:14-24`) generalized from the one `VIS_GRAPHICS_RVT_LINKS` parameter to every `BuiltInParameter` the chosen property groups touch; a locked pair is flagged **template-controlled — skip** in the preview rather than silently no-op'ing, with the same "edit template / remove template / cancel" three-way choice `ToggleLinked.pushbutton` already offers (`script.py:45-60`), scoped per template rather than per run.
5. **Preview table** — one row per (property group, target view), showing will-copy / already-matches / template-locked-skip, unticked rows pre-excluded, same resolve-preview-tick-write shape every other batch tool in the repo already uses.
6. **Apply** — one `Transaction`, generalizing `Copy Rebar Visibility.pushbutton`'s own commit/rollback block (`script.py:205-264`); a per-view failure is caught and reported without aborting the rest of the run, matching that tool's existing per-call `try/except`.
7. **Report** — copied / already-matched / template-locked / failed counts per view and property group, shown in the same info/success/error badge triplet the source tool already renders (`script.py:153-169`).

**Implementation:**
- New `anongee_toolkit.revit.view_graphics` module — the genuinely new piece, since none of `GetCategoryOverrides`/`SetCategoryOverrides`/`GetViewRange`/`SetViewRange`/`SetWorksetVisibility` exist anywhere in the toolkit today (confirmed by the repo-wide grep above): one read function per property group returning a plain snapshot from the source view, one apply function writing that snapshot onto a target view, and one `template_controls(view, doc, builtin_param)` helper lifted straight out of `ToggleLinked.pushbutton/script.py:14-24` and parameterized instead of hardcoded to `VIS_GRAPHICS_RVT_LINKS`.
- Filter copy reuses the `AddFilter`/`SetFilterOverrides` call shape already proven in `cad2bim/builders/view_filters.py:170-171`, but sourced from `View.GetFilters()` + `View.GetFilterOverrides(id)` on the chosen source view instead of a filter this same run just created.
- View/target enumeration goes through `anongee_toolkit.revit.views.get_eligible_views()` (`revit/views.py:30-56`) rather than the hand-rolled `FilteredElementCollector(doc).OfClass(View)...` block `Copy Rebar Visibility.pushbutton/script.py:289-296` still carries — both tools converge on the one shared helper.
- UI shell (`ui.xaml`, the source-combo/target-checklist/badge layout, `_flush_ui`'s `Dispatcher.Invoke` pattern) is a direct copy-and-extend of `Copy Rebar Visibility.pushbutton`'s own `ui.xaml` and `script.py`, adding one more panel of property-group checkboxes above the existing target list.
- New `view_graphics_sync_config.json` alongside `script.py` (which property groups default on, whether workset visibility is offered when the document isn't workshared — hidden rather than shown-disabled), mirroring `slab_convert_config.json`'s override-by-config shape.
- Sits in `Essential.panel/Bulk Tool.stack/`, next to `Copy Rebar Visibility.pushbutton`, with its own `bundle.yaml`/`CHANGELOG.md` since, like `AutoLevel.pushbutton`, this is a tool likely to grow more property groups (annotation categories, linked-model category visibility, phase filters) over time.

**Future update:**
- Fold `Copy Rebar Visibility.pushbutton`'s own rebar-specific hide/`Unobscured`/`Solid` logic in as one more property group once this tool is proven in production, so the two converge into one and a modeler doesn't need to run two separate "copy from this view" tools back to back.
- Saved, named view-graphics profiles (a captured snapshot, not tied to a live source view) reusable across sessions and projects — the same "save the rule set, not just the one-off copy" step the already-logged Universal Renamer and Grid & Level Extent Sync ideas both end on.
- Drift re-check mode: re-run against the same source/target pairing later in the project and report which target views have since diverged, rather than only ever doing a one-shot push.
- Extend past model views to Legends and Drafting Views' filter lists, and to linked-model category visibility (generalizing `ToggleLinked.pushbutton` fully rather than leaving it as the one-category special case it is today).

## 2026-09-15 00:39 UTC

**Idea name:** Grid & Level Extent Sync — batch 2D-extent and bubble-visibility propagation for datum planes across every structural view

**Potential:**
Every plan, section and elevation a modeler opens shows the model's grids and levels at whatever 2D extent and bubble on/off state Revit last happened to leave them at in *that specific view* — a `Grid`/`Level` is one model element, but its visible endpoint and whether its bubble shows are **per-view overrides**, so a project with 12 structural plans and 8 grids means up to 96 independent bubble/extent states a modeler drags and toggles by hand, one grid, one end, one view at a time, and redoes every time a new plan is duplicated or a grid is added mid-project. Revit's own "Reset to 3D Extents" is the only native shortcut, and it only ever restores the family's default 3D extent in that one view — it cannot copy a chosen, tidied extent-and-bubble pattern from a view a modeler has already cleaned up onto the other eleven, and it works one grid end at a time, never as a batch across a view set. The pieces this needs already exist in this repo, built for an entirely different job and never exposed to a button: `anongee_toolkit.structural.grids.grids(doc)` (`anongee_toolkit/structural/grids.py:25-33`) already reads every `Grid` in the model into `{name: Grid}`, and `segment_mm(grid)` (`grids.py:40-53`) already reduces each one to a clean 2D line segment in millimetres — refusing a curved grid by name rather than approximating it, the same explicit-refusal posture `ConvertFloor.pushbutton` uses for its own unsupported cases — but the only callers of that module today are `structural/inventory.py`, `structural/structure_run.py` and RC Automation's own `commands/grids.py`/`commands/_placement.py` (confirmed: grepping the whole toolkit for `structural.grids` turns up exactly those four, and none of them is a pushbutton), so it exists purely to cross two named grids into an `(x, y)` footing-placement point — never to read a grid's own line for a view-level operation. `anongee_toolkit.structural.levels.levels(doc)` (`structural/levels.py:19-28`) already returns every level sorted bottom-to-top, proven only inside `AutoLevel.pushbutton`'s own planner and the already-logged Column Stack Auditor and Sheet Set Builder ideas' stack/level enumeration — never for a Level's own per-view datum overrides. Nothing under `anongee_toolkit` or any `AnonGee.tab/**/script.py` calls `DatumPlane.SetDatumExtentType`, `SetCurveInView`, `GetCurvesInView`, `ShowBubbleInView`, `HideBubbleInView` or `IsBubbleVisibleInView` at all — confirmed by grepping every script for `DatumEnds`, `ShowBubble`, `HideBubble` and `SetDatumExtentType`, which return no hits anywhere in `AnonGee.extension` — so the entire per-view datum-override surface of the Revit API is untouched by this codebase today, on both the Grid and the Level side. On the market, propagating a cleaned-up grid/level extent-and-bubble pattern across a whole view set is sold only as one line item bundled inside paid whole-project drafting-production suites (CTC's and BIM One's grid/level tools, sold as part of a much larger licensed toolset); nothing free reads a "reference" view's own per-grid state and replicates it, view by view, across the rest of a set.

**Description:**

**Potential:**

Worse, every dimension `AutoDIM` places is scoped to exactly what got selected: `dimension_element()` draws one float dimension across a single element's own faces, and `dimension_datums()` (`script.py:254-302`) chains a dimension between whatever 2+ grids/levels happen to be in that one selection — neither ever builds the object a structural plan actually needs, a single continuous dimension **string** referencing every column centerline along one shared grid line in one `ReferenceArray`, ordered end to end; that requires re-selecting and re-running per row today, and nothing assembles the row automatically. `RoundElementDist.pushbutton` already proves the missing piece exists half-built next door — `build_direction_groups(elements, tol)` (`script.py:169-201`) already clusters walls/columns into rows sharing one axis/angle, and `place_dimension()` (`script.py:683-701`) already builds a `ReferenceArray` + `doc.Create.NewDimension` off it — but only ever between exactly **two** elements (a datum and one target), for its own "does this element sit where the datum says" QA job; it stops one reference short of chaining a whole row. **Description:**
`Dimension Sweep.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `AutoDIM.pushbutton` — this calls AutoDIM's own engine rather than re-implementing it) runs in one window:

1. **Scope & categories** — active view only (dimensions are view-specific, same constraint `AutoDIM` already enforces via `_NO_DIM_VIEWS`, `script.py:34-37`), tick which categories to sweep: Structural Columns, Structural Framing, Walls, and/or Grids/Levels — no selection needed, the whole point being to replace `revit.get_selection()` with a full collector.
2. **Cluster into rows** — every ticked element collected via `FilteredElementCollector(doc, active_view.Id)`, then bucketed by shared axis/angle using `build_direction_groups()` lifted out of `RoundElementDist.pushbutton` (same clustering, second caller — the same "one function, two callers" promotion the already-logged Grid Mark Assistant idea proposes for that tool's `_distance_to_line`); grids/levels cluster the same way `dimension_datums()` already groups a manual selection, just run across every datum in the view instead of only a chosen few.
3. **Build one chained string per row** — the genuinely new piece: for a column/wall/framing row, every member's extreme-face reference (from `AutoDIM`'s own `planar_faces()`/`extreme_faces()`, unmodified) is collected into one `ReferenceArray` ordered by position along the row's axis and fed to a single `doc.Create.NewDimension` — one continuous string, not `dimension_element()`'s N isolated per-element floats; a grid/level row calls `dimension_datums()` exactly as it exists today, unchanged.
4. **Duplicate-run guard** — the other genuinely new piece neither source tool has: before building anything, `FilteredElementCollector(doc, active_view.Id).OfClass(DB.Dimension)` is read and each existing dimension's `.References` compared against a row's computed reference set; a row whose references are already fully covered by one existing dimension is marked **already dimensioned** and skipped by default, and a row that's a superset of an existing dimension's references (new columns added to an existing row since the last sweep) is marked **row changed — will replace**, so a re-run after a revision only ever adds or refreshes what actually changed instead of stacking a second string under the first.
5. **Preview checklist** (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`, the same shell `ConvertFloor.pushbutton` and `AutoDIM`'s proposed siblings already run on) — one row per detected chain: category, member count, axis, and status (**will place** / **already dimensioned** / **row changed — will replace** / **blocked**, with the exact block reason `dimension_element()` already returns — "no planar faces", "no element axis lies in the view plane", etc., `script.py:186-194` — surfaced per member instead of silently dropped), plus a **Locate** action per row that isolates the row's members in the view.
6. **Place** — one `Transaction`; a "row changed" row deletes its stale dimension (`doc.Delete`) before creating the replacement, everything else creates fresh; one bad row's reference failure rolls back only that row, the rest of the sweep continues.
7. **Report** — placed / replaced / skipped-already-dimensioned / blocked counts, with the block reasons grouped the same way `AutoDIM`'s own `main()` already prints per-note today (`script.py:338-339`), just rolled into one run summary instead of one console line per manual selection.

**Potential:**
Every RCC structure over a few storeys lives or dies on one invariant nobody in this repo currently checks against the model itself: a column at a given grid position has to actually stand on the column below it, storey after storey, or the load path it is drawn to carry does not exist. Nothing clusters these into vertical stacks and walks them for continuity, offset or rotation drift. On the market, "column verticality/continuity checking" is sold only as one line item bundled inside paid whole-model QA/clash suites (Naviate/Symetri's Model Checker family, BIM One's structural QA tools, Revizto's rule checks) that charge per seat for a whole toolset a modeler does not need the rest of; nothing free reads Revit's own structural columns and reports "this stack breaks at Level 6" on its own.

1. **Scope** — whole model, or a category-filtered selection (reusing the scope/category picker pattern `Parameter Combine.pushbutton`'s `ScopePickerApp` already ships), Structural Columns only for v1 (walls are a future item, see below).

3. **Walk each stack, flag per adjacent pair**:
   - **Missing** — a level has a column in the stack above and below it but none at that level itself.

   - **Level-chain gap/overlap** — the lower column's top level + top offset does not land at the elevation of the upper column's base level + base offset (reading the same `FAMILY_TOP_LEVEL_PARAM` / `FAMILY_TOP_LEVEL_OFFSET_PARAM` / `FAMILY_BASE_LEVEL_PARAM` / `FAMILY_BASE_LEVEL_OFFSET_PARAM` parameters `columns.create()` already writes at `anongee_toolkit/structural/columns.py:270-275`), reported as a gap or overlap in mm.

5. **Report only** — this tool never writes to the model; it is a checker, not a fixer, since which fix is right (delete the extra column, move it back, or accept the offset as a deliberate architectural decision) is a judgement call for the modeler or the structural engineer, not a batch action.
