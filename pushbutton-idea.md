## 2026-09-14 05:39 UTC

**Idea name:** Schedule Round-Trip — push edited Excel values back into the exact Revit parameters `Export Schedule.pushbutton` only ever reads out

**Potential:**
`Export Schedule.pushbutton` already solves the hard half of getting a Revit schedule into a spreadsheet a non-Revit person can work in: `export_schedules_to_excel()` (`Export Schedule.pushbutton/script.py:455-666`) drives Revit's own `sched.Export(_TEMP_DIR, fn, opt)` (`script.py:521`) through a `ViewScheduleExportOptions` configured for tab-delimited output (`script.py:504-507`), parses the result with its own dependency-free `_parse_tsv_row`/`_read_tsv` (`script.py:172-201`), normalizes every cell's units via `_strip_unit()` (`script.py:232-275`) so `"230 mm"` becomes a real number, and even temporarily unhides every hidden field inside a `Transaction`, exports, then restores the original hidden state afterward (`script.py:509-519` unhide, `:523-528` restore) so a hidden QA column can be included without permanently exposing it in the model. But the whole pipeline runs in exactly one direction: nothing calls `openpyxl.load_workbook` to read a copy of that same export back in after a modeler hands it to a structural engineer or a quantity surveyor for review, gets 40 corrected column Marks, 200 revised rebar "ITEM_V" details, or a QS's bulk-corrected footing sizes back, and then has to manually retype every one of those changed cells into Revit one element at a time — the exact same one-way ceiling `Parameter Migrator`'s own writeup (already logged above) works around for parameter-to-parameter moves, but never for "values a person edited outside Revit." Revit's own native schedule export has no import counterpart at all through the UI, and the team has already named this exact class of gap once, on the export side: `todo-list.md:1018`'s `FEAT-44` records the owner's own words — *"Revit's native schedule will not take every parameter an element has... generate the table from the model — read every parameter, including the ones a native schedule refuses, and write it"* — which is about getting more data **out**, not about getting corrected data safely back **in**, so the write-back gap this idea targets survives even after FEAT-44 ships. The read-a-spreadsheet-into-Revit half exists in the codebase, but for a completely different job: `anongee_toolkit/rc_automation/excel_engine.py:444` (`read_grid`) already opens a workbook via `openpyxl.load_workbook` (`excel_engine.py:494,504`) — the only other `openpyxl` read anywhere in the repo (confirmed: no `AnonGee.tab/**/script.py` outside `Export Schedule.pushbutton` and `CPython3 engine.pushbutton` even imports `openpyxl`) — but it is built to parse RC Automation's own fixed placement-schedule format (`#SHEET,<name>` markers, per `rc_automation/excel_engine.py`'s own `done-list.md:27-29`), not to diff an arbitrary edited schedule export against live model parameters. The one real technical wall neither tool has to cross today: `sched.Export()`'s TSV output (`script.py:521`) carries no `ElementId` column unless the schedule itself happens to already have one configured, so an edited row cannot be matched back to the right element without one — but `Export Schedule.pushbutton` already proves, in its own `include_hidden` toggle, the exact "temporarily mutate the schedule's field list, export, put it back" mechanism this needs one field further. On the market, this exact capability — edit a Revit schedule in Excel, push the edits back into the model — is sold as the flagship, per-seat-licensed feature of Ideate BIMLink, Excelerator BIM's Sync tools, and similar "push/pull" add-ins; Revit itself has no native import path for a schedule at all, and nothing free replicates it.

**Description:**
`Schedule Round-Trip.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `Export Schedule.pushbutton`, reusing its dialog shell and export engine rather than re-implementing them) runs in two linked modes from one window:

1. **Prepare for edit** — reuses `Export Schedule.pushbutton`'s own schedule-picker list and search box (`ExportScheduleDialog._populate`/`_on_search_changed`, `script.py:329-344, 354-359`) to pick one or more schedules, then runs the same export pipeline (`export_schedules_to_excel`, `script.py:455-666`) with one addition: before exporting, for any schedule that doesn't already carry one, it temporarily adds a scheduled "Element Id" field and marks it hidden, using the identical `Transaction`-wrapped toggle `include_hidden` already performs at `script.py:509-519` (add/unhide → export → `script.py:523-528`-style restore, extended to remove the added field afterward instead of just re-hiding it) — so the round-trip workbook looks exactly like a normal `Export Schedule.pushbutton` output plus one extra key column, styled with the same `_BR_*` brand constants (`script.py:147-168`) so it visibly belongs to this tool.
2. **Edit outside Revit** — the modeler (or the engineer/QS they hand it to) edits any writable cell in the `.xlsx`, leaving the Element Id column untouched; no Revit session needs to stay open.
3. **Import & diff** — pick the edited workbook back in the tool; it loads it via the same bundled-runtime guard `Export Schedule.pushbutton` already proves (`_ensure_bundled_openpyxl()`, `script.py:91-118`), resolves each row's Element Id to a live element via `doc.GetElement`, and for every other column resolves the schedule field back to its real `Parameter` on that element (the one genuinely new piece: matching a `ScheduleField` to a writable `Parameter`, falling back through the same `BuiltInParameter → shared GUID → name` order `ConvertFloor.pushbutton`'s `find_target_param()` already uses, `ConvertFloor.pushbutton/script.py:866-886`), then compares the cell's value against the parameter's current value via `anongee_toolkit.revit.parameters.get_parameter_value` (`revit/parameters.py:36-82`).
4. **Preview checklist** (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`, the same shell `ConvertFloor.pushbutton` and `Parameter Migrator`'s proposed tool already run on) — one row per **changed cell**, not per exported row, showing element, schedule column, old value, new value, and status: **will write** / **unchanged** / **blocked — read-only parameter** / **blocked — element deleted since export** / **blocked — value/type mismatch**; blocked rows pre-unticked and un-tickable, same posture every other checklist tool in the repo uses.
5. **Apply** — one `Transaction`, writing every ticked change via `anongee_toolkit.revit.parameters.set_parameter_value` (`revit/parameters.py:85-113`), wrapped so one bad write doesn't roll back changes already committed for other elements in the same run.
6. **Report** — changed / unchanged / blocked counts per schedule, exportable via the same `openpyxl` write path `export_schedules_to_excel` already proves, so the round-trip leaves the same kind of audit artifact every other Excel-driven tool in the repo produces.

**Implementation:**
- Promote the field-hide/unhide toggle pattern already proven at `Export Schedule.pushbutton/script.py:509-519, 523-528` into a small shared helper in a new `anongee_toolkit.revit.schedule_io` module, extended to temporarily **add** a scheduled Element Id field rather than only toggle `IsHidden` on existing ones — the module's only genuinely new Revit API surface, since nothing in the repo currently adds or reads a schedule's field-to-parameter mapping.
- Field → parameter resolution in the same module reuses `ConvertFloor.pushbutton`'s exact matching order from `find_target_param()` (`ConvertFloor.pushbutton/script.py:866-886`: `BuiltInParameter` first, shared `GUID` second, name lookup last) rather than inventing a second matching convention.
- Read/write of individual parameter values goes through `anongee_toolkit.revit.parameters.get_parameter_value`/`set_parameter_value` (`revit/parameters.py:36-82, 85-113`) exactly as `Parameter Migrator`'s proposed tool above plans to be the first direct caller of that module — this tool becomes the second, sharing one read/write engine instead of a third bespoke parameter-setter.
- Excel read reuses `_ensure_bundled_openpyxl()` (`Export Schedule.pushbutton/script.py:91-118`) for the runtime guard, and the export half reuses `export_schedules_to_excel()`'s brand styling constants (`script.py:147-168`) and `_strip_unit()` (`script.py:232-275`) unchanged, so a round-trip workbook is visually and numerically identical to a normal export.
- `schedule_roundtrip_config.json` alongside `script.py` (which categories/fields are writable by default, conflict policy when the model value changed since export as well as the spreadsheet cell, Element Id column name/position), mirroring `slab_convert_config.json`'s override-by-config shape.
- Same modeless window shell (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`/`theme`) every other multi-step tool in the repo runs on.
- Sits in `Essential.panel/Action.stack/`, next to `Export Schedule.pushbutton`, its natural sibling and the tool it forks its export half from.

**Future update:**
- Lock the Element Id column with openpyxl cell/sheet protection so it survives a careless edit or column reorder in Excel, rather than only documenting "don't touch this column" in the UI.
- Feed "blocked — value/type mismatch" rows into `anongee_toolkit.revit.units` (`strip_unit`/`mm_to_ft`/`ft_to_mm`), the same module `Parameter Migrator`'s proposed tool already plans to reuse, so a QS's `"230mm"` typed into a numeric cell parses cleanly instead of blocking.
- Two-way live sync mode, matching the sync posture already proposed as a future item for `Type Matrix Generator`: re-import the same workbook after a later revision and diff again, rather than requiring a fresh export/edit/import cycle each time.
- Multi-schedule batch import (drop a folder of edited workbooks, one per discipline or trade, and reconcile all of them in one run) for firms that split schedule review across multiple reviewers in parallel.

## 2026-09-14 00:39 UTC

**Idea name:** Dimension Sweep — whole-view, chained dimension-string batching built directly on AutoDIM's own per-element engine

**Potential:**
`AutoDIM.pushbutton` already solves the hard geometry problem of reading an element's own extents along whichever of its axes lie in the current view plane (`element_frame`/`planar_faces`/`extreme_faces`/`extent_along`, `script.py:69-143`) and placing a clean, correctly-offset dimension off them (`dimension_element`, `script.py:183-237`), but `main()` only ever acts on `revit.get_selection()` (`script.py:312`) — a modeler has to manually multi-select every column, wall and beam that needs a dimension, run the tool, then reselect the next group and run it again, bay by bay and row by row, for the same 40-150-element plan the already-logged Bay Fill idea calls out for slab placement — the identical "click through every instance by hand" tax, just spent on annotation instead of modeling. Worse, every dimension `AutoDIM` places is scoped to exactly what got selected: `dimension_element()` draws one float dimension across a single element's own faces, and `dimension_datums()` (`script.py:254-302`) chains a dimension between whatever 2+ grids/levels happen to be in that one selection — neither ever builds the object a structural plan actually needs, a single continuous dimension **string** referencing every column centerline along one shared grid line in one `ReferenceArray`, ordered end to end; that requires re-selecting and re-running per row today, and nothing assembles the row automatically. `RoundElementDist.pushbutton` already proves the missing piece exists half-built next door — `build_direction_groups(elements, tol)` (`script.py:169-201`) already clusters walls/columns into rows sharing one axis/angle, and `place_dimension()` (`script.py:683-701`) already builds a `ReferenceArray` + `doc.Create.NewDimension` off it — but only ever between exactly **two** elements (a datum and one target), for its own "does this element sit where the datum says" QA job; it stops one reference short of chaining a whole row. And neither tool checks what is already on the sheet: both `dimension_element()`'s and `dimension_datums()`'s `doc.Create.NewDimension` calls (`script.py:232`, `script.py:299`) fire unconditionally, so re-running `AutoDIM` on a row after a later revision (two columns added, one resized) stacks a second dimension line under the first instead of updating it, leaving exactly the kind of duplicate annotation clutter the already-logged Warning Auditor idea's "exact-duplicate instances" fix category exists to catch for model elements — but that idea's `doc.GetWarnings()` scan never looks at `Dimension` elements at all. On the market, "select everything, one dimension string per row, auto" is sold only as a bundled feature inside paid drafting-automation add-ins (CTC's dimensioning tools, BIM One's auto-dimension utilities, assorted Autodesk App Store add-ins priced per seat); Revit's own multi-pick dimension tool still requires picking every reference by hand, and nothing free reads a plan's own column/wall/framing rows and grid lines and strings them in one batched pass.

**Description:**
`Dimension Sweep.pushbutton` (new tool in `Essential.panel/Action.stack`, sibling to `AutoDIM.pushbutton` — this calls AutoDIM's own engine rather than re-implementing it) runs in one window:

1. **Scope & categories** — active view only (dimensions are view-specific, same constraint `AutoDIM` already enforces via `_NO_DIM_VIEWS`, `script.py:34-37`), tick which categories to sweep: Structural Columns, Structural Framing, Walls, and/or Grids/Levels — no selection needed, the whole point being to replace `revit.get_selection()` with a full collector.
2. **Cluster into rows** — every ticked element collected via `FilteredElementCollector(doc, active_view.Id)`, then bucketed by shared axis/angle using `build_direction_groups()` lifted out of `RoundElementDist.pushbutton` (same clustering, second caller — the same "one function, two callers" promotion the already-logged Grid Mark Assistant idea proposes for that tool's `_distance_to_line`); grids/levels cluster the same way `dimension_datums()` already groups a manual selection, just run across every datum in the view instead of only a chosen few.
3. **Build one chained string per row** — the genuinely new piece: for a column/wall/framing row, every member's extreme-face reference (from `AutoDIM`'s own `planar_faces()`/`extreme_faces()`, unmodified) is collected into one `ReferenceArray` ordered by position along the row's axis and fed to a single `doc.Create.NewDimension` — one continuous string, not `dimension_element()`'s N isolated per-element floats; a grid/level row calls `dimension_datums()` exactly as it exists today, unchanged.
4. **Duplicate-run guard** — the other genuinely new piece neither source tool has: before building anything, `FilteredElementCollector(doc, active_view.Id).OfClass(DB.Dimension)` is read and each existing dimension's `.References` compared against a row's computed reference set; a row whose references are already fully covered by one existing dimension is marked **already dimensioned** and skipped by default, and a row that's a superset of an existing dimension's references (new columns added to an existing row since the last sweep) is marked **row changed — will replace**, so a re-run after a revision only ever adds or refreshes what actually changed instead of stacking a second string under the first.
5. **Preview checklist** (`anongee_toolkit.ui.hostwnd`/`checklist`/`progressbar`, the same shell `ConvertFloor.pushbutton` and `AutoDIM`'s proposed siblings already run on) — one row per detected chain: category, member count, axis, and status (**will place** / **already dimensioned** / **row changed — will replace** / **blocked**, with the exact block reason `dimension_element()` already returns — "no planar faces", "no element axis lies in the view plane", etc., `script.py:186-194` — surfaced per member instead of silently dropped), plus a **Locate** action per row that isolates the row's members in the view.
6. **Place** — one `Transaction`; a "row changed" row deletes its stale dimension (`doc.Delete`) before creating the replacement, everything else creates fresh; one bad row's reference failure rolls back only that row, the rest of the sweep continues.
7. **Report** — placed / replaced / skipped-already-dimensioned / blocked counts, with the block reasons grouped the same way `AutoDIM`'s own `main()` already prints per-note today (`script.py:338-339`), just rolled into one run summary instead of one console line per manual selection.

**Implementation:**
- Promote `AutoDIM.pushbutton`'s `element_frame`, `planar_faces`, `extreme_faces`, `extent_along`, `classify` and `dimension_element` (`script.py:69-237`) into a shared `anongee_toolkit.revit.dimensioning` module so both the existing single-selection tool and this new sweep call one copy instead of a second implementation of the same face-reading math; `AutoDIM.pushbutton/script.py` becomes a thin caller of the promoted module, behaviour unchanged.
- Promote `RoundElementDist.pushbutton`'s `build_direction_groups()` (`script.py:169-201`) the same way, into `anongee_toolkit.revit.clustering`, so this tool, `RoundElementDist`, and the already-logged Grid Mark Assistant idea's grid-family clustering all import one function.
- New chain-builder function (the one piece with no existing equivalent): takes a row's members, orders them by their `bbox_center()` projection onto the row's shared axis (reusing `AutoDIM`'s existing `bbox_center()`, `script.py:146-150`), pulls each member's extreme-face `Reference` on that axis, and appends them into one `DB.ReferenceArray` in order before the single `NewDimension` call.
- Duplicate-guard reads `Dimension.References` off `FilteredElementCollector(doc, active_view.Id).OfClass(DB.Dimension)` and compares `ElementId`/`LinkElementId` sets against each candidate row's resolved reference set — no new Revit API surface, just a read nothing in the repo currently does against annotation elements.
- `dimension_sweep_config.json` alongside `script.py` (which categories default-ticked, row-changed replace-vs-skip default, minimum members per row to bother stringing), mirroring `slab_convert_config.json`'s override-by-config shape.
- Same modeless window shell (`anongee_toolkit.ui.hostwnd` / `progressbar` / `checklist` / `theme`) every other multi-step tool in the repo already runs on.

**Future update:**
- Fold back into `AutoDIM.pushbutton` itself as a mode toggle ("Dimension selection" vs. "Sweep view") once the shared `dimensioning`/`clustering` modules have two independent, proven callers — the same fold-back posture the already-logged Bay Fill idea proposes for `DrawFloor.pushbutton`.
- Two-tier stacking: an overall dimension string beneath each per-bay row showing the cumulative end-to-end length, matching the two-line dimension stack convention a real structural plan is drawn with, rather than the single string v1 produces.
- Multi-view batch mode: run the sweep across every plan view in a chosen view set (one pass per level) instead of the active view only, for a modeler dimensioning an entire building's structural plans in one sitting.
- Feed "row changed — will replace" counts into the already-logged Warning Auditor's proposed trend CSV, so a weekly model-health snapshot can show how much dimension rework a revision caused, the same axis that idea's own future items propose for warning counts.

## 2026-09-13 15:39 UTC

**Idea name:** Type Consolidator — find every duplicate/near-duplicate type sharing one identical structure, merge every instance onto one canonical type, purge the rest

**Potential:**
Every model that gets copy-pasted between projects, linked in from a consultant, or built by more than one modeler ends up with the same wall or floor type created twice under two different names — `200mm RCC Wall` and `WALL - 200 RCC` with byte-identical compound structures, or a slab type re-created after a paste-align instead of picked from the Type Selector — and both stick around because both are *in use*, so Revit's own `Purge Unused` (which only drops types with zero instances) never touches either one. The result compounds every day after: the Type Selector for every category grows a second, third, fourth near-duplicate entry a modeler has to visually diff before picking the right one, schedules split one real assembly into two rows, and the file carries the weight of both. Nobody in this repo currently reads the model for this: `ConvertFloor.pushbutton` already builds the exact signature this needs — `cs_signature(ftype)` (`ConvertFloor.pushbutton/script.py:704-716`) reduces a `CompoundStructure` to a tuple of `(layer width, material id, layer function)` per layer, and `resolve_type()`'s `"identical layers"` branch (`script.py:756-759`) already uses that signature to treat two same-structure types as interchangeable — but only to pick a *conversion target* for one element at a time inside one run, never to sweep the whole model and report every group of types that collapses to the same signature. `anongee_toolkit.structural.inventory.gather()` (`anongee_toolkit/structural/inventory.py:33-48`) already walks every category and family in the model for the template-audit report `Extract Template.pushbutton` produces, so the "what types exist" enumeration exists too, just never grouped by structural identity or fed a merge action. The instance-reassignment half is proven elsewhere in the repo under a different name: `structural/stairs.py:224,339` and `cad2bim/builders/stairs.py:211` already call `element.ChangeTypeId(new_type_id)` to swap a placed instance onto a different type/symbol id, and `operations/bulk_delete.py`'s `RevitTransaction`-wrapped `GenericBulkDeleteDialog` (`operations/bulk_delete.py:90,222`) already proves the "collect candidates, tick which to remove, one transaction" shape for exactly the case of deleting now-orphaned style/pattern elements. Nothing wires these three proven pieces — structure signature, model-wide grouping, reassign-then-delete — into one tool. On the market this is sold only as "purge / clean-up" line items inside paid whole-model housekeeping add-ins (Ideate Sidekick's "Purge" and BIM One's "eTools"-class utilities, both licensed per seat for a much larger bundle); the free option is Revit's own Purge Unused, which by definition cannot see a duplicate that is still in use, and no free tool groups in-use types by identical structure and reassigns instances before deleting.

**Description:**
`Type Consolidator.pushbutton` (new tool in `Essential.panel/Bulk Tool.stack`, alongside `Bulk Delete.pulldown` / `Bulk Rename.pulldown` — a housekeeping tool in the same family, one step past what either already does) runs in one window:

1. **Scope** — pick one or more system-family categories to scan (Walls, Floors, Roofs, Structural Foundations first, since all four expose `GetCompoundStructure()`; loadable-family categories — Structural Columns, Framing, doors/windows — follow in a second pass, matched on identical instance/type parameter values instead of a compound structure, via the same `get_parameter_value` sweep `Parameter Migrator`'s proposed tool above already plans to promote from `anongee_toolkit.revit.parameters`).
2. **Group by identity** — every type in scope reduced to `cs_signature()` (promoted out of `ConvertFloor.pushbutton` into a shared `anongee_toolkit.revit.types` module rather than re-implemented), types sharing one signature clustered together; each cluster ranked to propose a **canonical type** (most-used by instance count, ties broken by oldest `ElementId` so the type more likely referenced by a firm standard wins over a stray paste-in).
3. **Preview checklist** — one row per non-canonical type in a cluster: its name, instance count, the canonical type it would merge into, and a **parameter-loss** flag if any writable instance parameter values on its instances don't already match what the canonical type's own instances carry (reusing the "list what doesn't survive" posture `ConvertFloor.pushbutton`'s own checklist already uses) — so a modeler can untick a type that only *looks* identical in structure but is tracked separately on purpose (a firm sometimes keeps twin types for scheduling reasons), rather than the tool silently assuming structure equality means intent equality.
4. **Merge** — one `TransactionGroup`, per ticked type: every instance's `ChangeTypeId()` (the same call `structural/stairs.py` and `cad2bim/builders/stairs.py` already make) repointed at the cluster's canonical type id, then the now-orphaned type deleted with `doc.Delete(type_id)` inside the same `RevitTransaction` shape `operations/bulk_delete.py`'s `GenericBulkDeleteDialog` already runs, so one type's instances failing to reassign (locked, in a group, in a linked/nested family) rolls back only that type and the rest of the merge continues.
5. **Report** — clusters merged / instances repointed / types deleted / skipped-parameter-mismatch, exportable via the same `openpyxl` path `Export Schedule.pushbutton` and `BBS Generator.pushbutton` already use, so a "before/after Type Selector count" line exists for a handover or a file-size review.

**Implementation:**
- Promote `cs_signature()` and the `"identical layers"` matching it already backs (`ConvertFloor.pushbutton/script.py:704-759`) into a new `anongee_toolkit.revit.types` module, so both `ConvertFloor.pushbutton`'s single-element conversion lookup and this tool's whole-model grouping call one shared function instead of a second copy.
- Loadable-family matching (columns/framing/doors/windows, no `CompoundStructure` to read) reuses `anongee_toolkit.revit.parameters.get_parameter_value` (`revit/parameters.py:36`) across every writable type parameter to build an equivalent signature tuple, keyed by family name + parameter values rather than compound layers.
- Instance discovery per type is `FilteredElementCollector(doc).OfCategoryId(cat_id).WhereElementIsNotElementType()` filtered by `element.GetTypeId() == type_id`, no new API surface.
- Reassignment is the existing `ChangeTypeId()` call already proven at `structural/stairs.py:224,339` and `cad2bim/builders/stairs.py:211`; deletion afterward follows `operations/bulk_delete.py`'s own `RevitTransaction`-per-item shape (`operations/bulk_delete.py:222`) rather than a new transaction pattern.
- `type_consolidator_config.json` alongside `script.py` (which categories are in scope by default, whether a parameter-mismatch row blocks the merge or just warns, canonical-type tie-break rule), mirroring `slab_convert_config.json`'s override-by-config shape.
- Same modeless window shell (`anongee_toolkit.ui.hostwnd` / `progressbar` / `checklist` / `theme`) every other multi-step tool in the repo already runs on.
- Excel report reuses the `openpyxl` path already proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton`.

**Future update:**
- Fold in `anongee_toolkit.structural.inventory.gather()`'s existing per-category enumeration (`structural/inventory.py:33-48`) so a consolidation run doubles as an update to the same template-audit report `Extract Template.pushbutton` already produces — "N duplicate types found" becomes one more line in a model-health snapshot.
- A "near-miss" tier below exact signature match — same layer count and materials, thickness within the same `thickness_tolerance_mm` convention `ConvertFloor.pushbutton`'s config already uses — surfaced as **review, not auto-grouped**, for the case of two types one millimetre apart that were never meant to be the same.
- Cross-project mode: run the same signature grouping against a firm's shared type-catalogue project and flag which in-project types already match a standard type by structure, closing the loop from "duplicate found" to "replaced with the firm-standard type," not just "collapsed to whichever instance count won."
- Feed the merge report's "instances repointed" list into `Warning Auditor`'s duplicate-Mark category once both exist, since a merge that repoints two previously distinct types onto one can surface a Mark collision that was invisible while the types were still separate.

## 2026-09-13 10:45 UTC

**Idea name:** Bay Fill — one-pass batch slab placement across every enclosed structural bay `DrawFloor.pushbutton` already finds but only lets you click one at a time

**Potential:**
`DrawFloor.pushbutton` already solves the hard geometry problem of "find every enclosed region bounded by beams and columns in this plan" — it reads exact footprints, splits them into a planar graph and traces closed cycles into candidate faces (`build_graph`/`trace_faces`/`FaceIndex`, `DrawFloor.pushbutton/script.py:674-806`), then filters them down to a real, already-computed list of usable regions (`usable = [f for f in faces if abs(signed_area(points, f)) >= MIN_FACE_AREA]`, `script.py:1255`) before the user ever touches the mouse. But `main()`'s only way to turn a face into a slab is `draw_session()`'s `while True: uidoc.Selection.PickPoint(...)` loop (`script.py:1306-1397`), which places exactly one `Floor.Create` per click (`script.py:1368`) and never walks the `usable` list it already built end-to-end — a modeler filling a podium or a typical floor plate with 40–150 structural bays clicks every single one by hand, waits for the pick prompt each time, and gets no indication of which bays remain. Worse, nothing in the file checks whether a bay already has a floor in it (no `OST_Floors` collector anywhere in `script.py` besides the type-picker at `script.py:1106`), so re-running the tool after a later revision adds a few new beams means either re-clicking only the new bays from memory or risking a stacked duplicate floor in a bay already filled. This is exactly the "type generator"/batch-modeling chore the team already funds elsewhere in the toolkit (`AutoDIM.pushbutton` has the identical gap — it dimensions only the current selection, never every column or grid-bay in a view in one run) applied to the single most repetitive slab-modeling task a structural BIM modeler does. On the market, "create floor by enclosed boundary" exists only as Revit's own native `Create Floor > Pick Walls`/mass-face tools (which need a wall loop or a modeled mass face, not beam/column outlines, and place one floor per manual sketch anyway) or as one feature bundled inside paid whole-project automation suites (AGACAD, CTC); nothing free reads real beam/column geometry and fills every enclosed bay in a view in a single confirmed batch.

**Description:**
`Bay Fill.pushbutton` (new tool in `Essential.panel/StrucBIM.stack`, sibling to `DrawFloor.pushbutton`, reusing its scan pipeline rather than re-implementing it) runs in one window:

1. **Scan** — calls `DrawFloor`'s own `build_regions(view)` (`script.py:1218-1299`) to get the full, already-cached `usable` face list for the active view — same session cache (`CACHE_KEY`/`signature`/`load_cached`/`store_cached`, `script.py:168,1177-1211`) and the same SHIFT-click-to-force-rescan convention, so switching between DrawFloor's click mode and this batch mode in one session never forces a redundant re-scan.

**Potential:**

- New `anongee_toolkit.revit.warnings` module: `doc.GetWarnings()` → group-by-GUID, a GUID→category lookup table (with a text-match fallback for unmapped GUIDs across Revit versions), and one fix function per auto-fixable category — kept separate from any one button's `script.py`, the same separation `anongee_toolkit.revit.geometry`/`transactions` already give `ConvertFloor.pushbutton`.

**Idea name:** Sleeve & Opening Coordinator — MEP-clash-driven structural opening placement, sizing rules and blocked-zone reporting

**Potential:**
Every RCC project with MEP in the model or linked in hits the same weekly grind: a clash report (Navisworks export, or the linked MEP model itself) names 40–300 pipe/duct/conduit crossings through beams, walls, slabs and footings, and a modeler works through them one by one — measure the pipe/duct diameter and angle, check it against the beam's depth and the code's max-opening-to-depth ratio, check it isn't inside a column strip or too close to a support, place a generic opening or sleeve family at the right host/location/rotation, and tag it back to the clash ID for the MEP team to trace. Fifteen to forty crossings an hour by hand is optimistic once beam-depth and edge-distance checks are done properly instead of eyeballed, and a missed edge-distance check is exactly the kind of thing that surfaces as a site RFI months later. Every existing tool in the repo that touches structural elements (`ConvertFloor.pushbutton`, `RC Automation.pushbutton`, `RoundElementDist.pushbutton`) works host-by-host on elements already selected or already scoped by category — none of them read a second, MEP-side model and turn its crossings into structural openings; that geometry-intersection step doesn't exist anywhere in `anongee_toolkit` yet (`revit/geometry.py` has none, and there's no `sleeve`/`opening` module under `structural/`). On the market, this exact workflow is sold as a paid module inside larger BIM-coordination suites (Naviate/Symetri's openings tool, BIMOne's sleeve manager) — nothing free does clash-in, sized-and-code-checked-opening-out for Revit natively.

**Description:**
`Sleeve Coordinator.pushbutton` (new tool in `Essential.panel/StrucBIM.stack`, sibling to `Convert Slab.pushbutton` and `RoundElementDist.pushbutton`) runs in one window:

1. **Load crossings** — either import a Navisworks clash report (CSV/XML export, matched by element GUID/UniqueId back to the host Revit model) or scan directly: pick a linked MEP model (or a category set in the same model), pick the structural host categories (Structural Framing, Walls, Floors, Foundations), and the tool geometrically intersects MEP curve-based elements (pipes, ducts, conduits, cable trays) against host solids to build the same crossing list itself, one row per penetration.
2. **Resolve & size** — per crossing, works out opening shape (circular for pipe/conduit/round duct, rectangular for rectangular duct/tray) and size from the MEP element's diameter/width-height plus a configurable clearance allowance; checks it against per-category rules (max opening size as a fraction of beam depth/width, minimum edge distance from any column/support face or from another opening, no penetration inside a defined column-strip/shear-wall-boundary zone) — same shape as `ConvertFloor.pushbutton`'s pre-flight plan: every row resolves to **place** / **blocked** with the specific rule it failed.
3. Preview checklist (`anongee_toolkit.ui.hostwnd` + `progressbar`, same shell `AutoLevel.pushbutton` and `Convert Slab.pushbutton` already use): tick rows to place, blocked rows pre-unticked with the reason shown, each row tagged with the source clash ID for traceability.
4. **Place** — creates (or updates, if a sleeve at that clash ID already exists) a host-based opening/sleeve family instance per confirmed row, sets its size/rotation/host parameters and a "Clash Ref" instance parameter back to the originating clash ID; one `TransactionGroup`, one `Transaction` per element, same rollback-per-element posture as `Convert Slab.pushbutton`.
5. **Report** — result table (placed / blocked / updated / removed-because-crossing-no-longer-exists-on-rerun) exportable to Excel via the same `openpyxl` path `Export Schedule.pushbutton` and `BBS Generator.pushbutton` already use, so the MEP team gets back exactly the list they need to close their clash report against.

**Implementation:**
- New `anongee_toolkit.structural.openings` module: crossing detection (`Solid`/`Curve` intersection via `Autodesk.Revit.DB.BooleanOperationsUtils` or bounding-box-then-exact-solid test against each MEP curve swept as a thin solid), sizing/rule evaluation, and opening-family placement, following the same host-parameter-matching convention (`BuiltInParameter` → shared GUID → name) `ConvertFloor.pushbutton` uses for its own parameter carry-over.
- Reuses `anongee_toolkit.revit.geometry` for the low-level intersection/bounding-box helpers rather than duplicating them inline, and `anongee_toolkit.revit.transactions` for the per-element rollback pattern already proven there.
- Clash-report import: a thin CSV/XML reader matching Navisworks' export columns (test-name, item1/item2 GUIDs, clash point) to Revit elements via `UniqueId`; falls back to the direct-scan mode when no report is supplied, so the tool works even for teams that don't run Navisworks.
- Sizing/edge-distance rule set lives in a `sleeve_config.json` alongside `script.py`, mirroring `slab_convert_config.json`'s shape — per-category max-opening-ratio, min-edge-distance, clearance allowance, all overridable per project/firm standard.
- Opening family itself: ships one parametric round + one rectangular generic-model-based-opening family (or a face-based void-cutting family, matching whatever the firm's existing opening family already is, if one exists in the extension's family library) with type parameters for diameter/width/height and an instance "Clash Ref" text parameter for traceability.
- Excel report reuses the `openpyxl` write path already proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton` — no new dependency.
- `bundle.yaml` / `README.md` / `CHANGELOG.md` layout following the root README's documented convention for versioned StrucBIM tools.

**Future update:**
- Re-run mode that diffs against the last placed set: crossings that moved get the sleeve relocated, crossings that vanished (pipe re-routed) get the orphaned sleeve flagged for removal instead of silently left behind.
- Feed blocked rows (opening too big for the beam, or inside a shear-wall boundary) straight into a structural-engineer review queue, cross-referenced by the same "Clash Ref" id, so a redesign request is one export away instead of a re-explained email.
- Extend past MEP crossings to structural-vs-structural coordination: a duct penetrating both a beam and the slab it frames into, reconciling the two openings into one that satisfies both hosts' rules.
- Multi-linked-model support (structural host model with two or more linked MEP disciplines — plumbing, HVAC, electrical — scanned in one pass), each discipline's crossings tagged separately in the report.

**Idea name:** Type Matrix Generator — Excel-driven bulk type creation, parameter sync and duplicate-type detection, across system families and loadable families

**Potential:**
Every structural revision that adds a new column/beam/wall size, or a schedule handed over by the engineer as "here are the 18 column sizes for this project," turns into the single most repetitive click-chain a BIM modeler does: open Type Properties, Duplicate, rename by hand, retype 3–6 dimension parameters, close, repeat — 2–4 minutes per type, 18 types is an hour of pure clicking, and a mistyped dimension on type 14 of 18 is invisible until a clash or a quantity take-off surfaces it. The toolkit already has a `type_name_mode` "convention" matcher baked into `ConvertFloor.pushbutton` and an Excel round-trip (`openpyxl`) proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton`, but nothing turns those two proven pieces into a general type factory — the closest thing, `BIMGeneration.pushbutton`'s "auto-sized type duplicates," is a hidden internal step of one INP-import workflow, not a tool a modeler can point at an arbitrary family and a spreadsheet. Revit's own answer, type catalogs, only works for loadable families that ship a `.txt` catalog and cannot touch system families (Structural Column, Structural Framing, Wall, Floor, Duct, Pipe) at all — which is exactly where a structural team's type churn actually happens. Paid market tools (e.g. Case/Ideate-style "batch type creator" add-ins) do the create-from-spreadsheet half for a fee; none of them add the other half this idea includes for free: scanning the project for types that are already duplicates of each other in every parameter but name, which is the silent bloat that makes a family's type list unusable a year into a project.

**Description:**
`Type Matrix Generator.pushbutton` (new `TypeTools.stack` in `Advance.panel`, alongside `Parameter Combine.pushbutton`) runs in three modes from one window:

1. **Generate from matrix** — pick a category + family (any loaded family, system or component), pick a base type to duplicate from, then load a CSV/XLSX where each row is a new type: a name column (or name-template tokens: `{b}x{d}`, `{Prefix}-{Index:03}`) plus one column per parameter to set (dimensions, material, structural usage, cost code, comments — anything writable on that family). 2. **Harvest to matrix** — the reverse: pick a category/family, tick which parameters matter, and export every existing type as a spreadsheet row — the fast way to hand an engineer "here is every column type in the model today" or to seed the input for mode 1 when duplicating a size series.
3. **Duplicate-type finder** — scan a category (or the whole model) for types whose full parameter set matches another type in the same family bar name, surface them as merge candidates with a usage count (how many instances use each), and — on confirm — repoint every instance of the duplicate to the kept type via `ChangeTypeId` before deleting the redundant type, same "what's lost, confirm per row" gate the conversion tools already use.

**Implementation:**
- Excel read/write via the `openpyxl` path already vendored for `Export Schedule.pushbutton` / `BBS Generator.pushbutton` — no new dependency.
- Row → type resolution: `Element.Duplicate` (or `ElementType.Duplicate`) for the create path, then set each mapped parameter by `BuiltInParameter` → shared GUID → name, exactly the matching order `ConvertFloor.pushbutton` already uses for its own parameter carry-over, so a name typo in the sheet falls back the same predictable way instead of silently no-op'ing.
- Name-template tokens reuse the same small `re`-based token formatter proposed for the Universal Renamer idea below (`{b}`, `{d}`, `{Index:03}`, a regex capture from an existing name) — if that tool lands first, this one imports its formatter instead of re-implementing it.

- One preview grid + Generate/Report-only toggle shared across all three modes, same modeless-window shell (`anongee_toolkit.ui.hostwnd` / `progressbar` / `theme`) `AutoLevel.pushbutton` already runs on, so the window behaves consistently with the rest of the toolkit.
- Sits in a new `TypeTools.stack` in `Advance.panel` next to `Parameter Combine.pushbutton` (its natural sibling — one sets instance parameter values, this sets type parameter values and creates the types themselves); own `bundle.yaml` tooltip and `CHANGELOG.md` since, like `AutoLevel`, it is a tool that will keep growing new source categories.

**Future update:**
- Two-way live sync mode: re-import the same sheet after an engineer edits it and diff against current model types, so a revised design table updates existing types in place instead of only creating new ones.
- Cross-project type library: save a matrix + base-family pairing as a firm-standard "type set" (e.g. "IS 456 column sizes 230–900mm"), reusable project to project without re-authoring the sheet.
- Extend the duplicate-type finder into a background/report-only health-check mode runnable on a schedule, surfaced next to the model's other cleanup tools (`Bulk Delete.pulldown`) as a periodic "type bloat" report.

**Idea name:** Convert Column ⇄ Wall — cross-category recreate for structural columns and shear/RC walls

**Potential:**
Mid-project structural revisions routinely flip vertical elements between the two systems a BIM modeler has zero built-in tooling to bridge: a lift core or stair shaft redesigned from a column grid into shear walls, a party/boundary wall that a revised scheme turns into a column line, or an architect's RFI that swaps a stub wall for a column so a door can open past it. It is squarely in the productivity bracket the team already funds, it is a direct sibling of a tool already shipped, and there is no free (or, as far as public listings show, even paid) Revit add-in that does a *bidirectional*, dependent-preserving Column ⇄ Wall recreate — the paid category-swap tools on the market handle system-family-to-system-family swaps (wall type to wall type) or rely on Revit's own Type Selector, which cannot cross `OST_StructuralColumns` ⇄ `OST_Walls` at all.

**Description:**
`Convert Column-Wall.pushbutton` (sibling to `Convert Slab.pushbutton` in `StrucBIM.stack`) converts selected Structural Columns to Structural (or Basic) Walls, and selected Walls back to Structural Columns, on a pre-selection or an interactive pick, in plan, 3D, section or elevation:

1. Reads the pre-selection, or prompts a pick filtered to the relevant category (columns when going →Wall, structural/basic walls when going →Column).
2. Builds a plan per element:
   - **Column → Wall:** the column's plan footprint (rectangular or the sketch of a non-rectangular profile) resolves to a wall location **line** (the long axis, or a user-chosen axis for a square column) and a **thickness** (the other side); base level + base/top offsets carry across as the wall's own; a column whose footprint isn't reducible to one straight line + thickness (an L/T-shaped or round column with no dominant axis) is flagged and blocked, same as `Convert Slab` blocks a non-horizontal sketch.
   - **Wall → Column:** a straight wall's length and thickness resolve to a rectangular column footprint at each end (or split into repeated column instances at a spacing the user sets, for a long wall being replaced by a column line) — curved or multi-segment walls are blocked with the reason named, same posture as isolated footings being out of scope for `Convert Slab`.

4. One `TransactionGroup`, one `Transaction` per element — a single failure rolls back only that element.
5. Result table with a geometry delta (footprint area / volume / centroid) per element, flagged the same way `Convert Slab` flags a delta over tolerance.

What survives: level + base/top offset, structural flag, phase, workset, pin state, all writable instance + shared parameters matched by BuiltInParameter → shared GUID → name (unmatched ones listed by name), joins and join order (recorded, re-applied via `SwitchJoinOrder`), and — the hard part that makes this worth building rather than hand-converting — **hosted rebar re-pointed to the new host** via `Rebar.SetHostId` before the original is deleted, exactly like `Convert Slab` already does for slab-hosted rebar. What's lost, reported per element for confirmation: tags, dimensions, face-hosted family instances (door/window openings on a converted wall have nowhere to go on a column and vice versa), parts, the ElementId itself.

**Implementation:**
- Fork `ConvertFloor.pushbutton/script.py` structurally rather than the code: same recreate → replay → delete → rejoin → rehost-rebar → verify pipeline, same `type_name_mode` (`"same"` 1:1 by name, `"convention"` prefix/suffix + dimension-tolerance matching), same model-group ungroup/convert/regroup handling for single-instance groups, same blocked-by-default posture for multi-instance groups and elements in assemblies/inactive design options.
- New geometry step neither existing tool needs: footprint → line+thickness resolution for Column→Wall (via the column's `BoundingBoxXYZ` / cross-section sketch, falling back to the family's cross-section parameters when available) and line+thickness → footprint for Wall→Column — this is the one genuinely new piece of logic; everything else (parameter carry-over, join preservation, group handling, checklist UX, transaction-per-element rollback) is lifted from `ConvertFloor.pushbutton` and `anongee_toolkit.ui`.
- Rebar rehost reuses the exact `Rebar.SetHostId` call already proven in `ConvertFloor.pushbutton`; the "what's lost" report reuses its `forms.confirm` gate naming every element whose dependents will be destroyed.
- New `column_wall_convert_config.json` alongside `script.py`, mirroring `slab_convert_config.json`'s shape (`type_name_mode`, `thickness_tolerance_mm`, `groups.multi_instance`, plus a new `wall_axis_mode: "long_side" | "prompt"` and `column_spacing_mm` for the wall→column split case).
- Sits in `Essential.panel/StrucBIM.stack/`, next to `Convert Slab.pushbutton`, using the same `bundle.yaml` / `README.md` / `CHANGELOG.md` layout the root README documents for versioned tools.

**Future update:**
- Extend the footprint resolver to L/T-shaped and round columns by decomposing into multiple straight wall segments instead of blocking outright.
- Wall→Column mode learns a "replace every column-spaced stretch of this wall" batch mode, for converting an entire shear-wall run back into a column-and-infill scheme in one pick.

**Idea name:** Universal Renamer — token templates + Excel mapping, across every renameable category

**Potential:**
Renaming to match a client's naming standard is one of the most repeated, most tedious tasks on a BIM team, and today it's done by hand, category by category, inside dialog boxes that only support simple find/replace. A model handover or a mid-project standard change (new discipline codes, new level naming, a merged project) can mean renaming 100+ sheets, views, levels, grids and schedules by hand — normally a half-day to a full day of pure clicking, with the real risk of dropped titleblock/view sync errors along the way. A token-driven, previewed, one-batch rename collapses that to minutes and removes the manual-error risk entirely. This is squarely in the productivity bracket the team already values enough to have built **Bulk Rename** for — it just stops short of the categories modelers actually rename most.

**Description:**
`Universal Rename.pushbutton` (or a new `Universal Rename.pulldown` sibling to the existing `Bulk Rename.pulldown`) extends renaming beyond Fill Patterns / Line Patterns / Line Styles to the categories a BIM modeler renames every week:

- Views (all types) and Sheets
- Levels and Grids
- Schedules and View Filters
- Family Types (within a family, e.g. duplicating a type-catalog row)

Two rename modes, selectable per run:
1. **Token template** — build a pattern from live tokens (`{Discipline}`, `{Level}`, `{ViewType}`, `{SheetNumber}`, `{OldName}`, `{Index:03}`, a regex capture group from the current name) and apply it across every selected/filtered element in one pass, e.g. turn `S-101 - Foundation Plan` into `STR-L00-FOUNDATION-PLAN`.

Both modes share one pipeline: filter (by category, by naming pattern, by pre-selection) → live preview table showing old name / new name / collision flags → user unticks anything wrong → single `Transaction`, one undo step → result report (renamed / skipped / collided), exportable back to Excel for a handover record.

- Token engine: small formatter over Revit's built-in parameters + regex capture groups pulled from the current name (`re.match` against a user-supplied pattern) — no new dependency, CPython3 stdlib `re` is enough.
- Excel mapping: reuse the `openpyxl` path already proven in `Export Schedule.pushbutton` / `BBS Generator.pushbutton` for read + the write-back report.
- Collision detection before the transaction opens (duplicate target names within the batch, or a target name already used elsewhere in the model) — block those rows, same "blocked rows pre-unticked" UX `Convert Slab` uses.
- Sits as a new pulldown/stack entry in `Essential.panel/Bulk Tool.stack/`, next to `Bulk Rename.pulldown`, following the same `bundle.yaml` / `ui.xaml` / `script.py` bundle layout documented in the root README.

- Extend token source to shared parameters, not just built-ins, so a firm-specific "Discipline Code" parameter can drive the template directly.
